# 設定項目メンテナンス方針

各 agent CLI の設定編集レジストリ（`SETTINGS_FIELDS`）と i18n を、各 CLI の公式仕様に追随して継続的に維持するための判定基準と手順を定める。設定項目の追加・廃止は各 CLI の更新に伴い随時発生するため、その都度この方針に従う。

対象レジストリの所在と型・保存の仕組みそのものは `システム仕様.md` の「設定編集レジストリ」を参照する。本書は「どのキーを登録／廃止し、どう型付けするか」の判定基準と作業手順を扱う。

## 2. 登録するキーの条件

次をすべて満たす「ユーザーが自分の設定ファイルに書けるキー」だけを登録する。

- 公式の設定リファレンス／スキーマ／ソースに存在する。
- マネージド専用でない（§3）。
- 非推奨（deprecated）・レガシー別名でない。正規キーのみを登録する。OpenCode は §7 の基準で判断する。
- 対象 CLI の設定ファイル自体のキーである。別ファイル（キーバインド、`pager.toml`、`tui.json` 等）は対象外。キーバインド設定は、設定ファイル内のキー（例: Codex の `tui.keymap`）も含めて本アプリの対応機能外とする。Grok の `keys.vim` はキーの割り当てではなく Vim ナビゲーションの切り替えなので登録する。
- サーバーからフェッチされるリモート設定専用フィールドでない（例: Grok の `RemoteSettings`）。

## 3. マネージド専用の除外

組織管理者が配布する管理ポリシー設定でのみ有効なキーは、既存・新規を問わず登録しない。製品ごとの該当パターン:

- **Claude**: `managed-settings.md` の「Keys only a managed source can set」に載るキー（`strictKnownMarketplaces`、`allowManaged*` 系、`sandbox.*.allowManaged*Only` など）と、`settings-reference.md` の Scope が Managed だけのキー。Scope が `Any file` か User を含むキー（例: `minimumVersion`、`askUserQuestionTimeout`）は登録対象とする。
- **OpenCode**: `enterprise`（central config）配下のキー。
- **Grok**: `RemoteSettings` 由来のリモート／管理フィールド（`managed_mcps.enabled` 等）、および `auth` / `grok_com_config.oidc` などの外部認証・enterprise 節。例外として `auth.auth_provider_command`（別名 `grok_com_config.auth_provider_command`）と `auth_provider.<name>` は利用者のコマンド設定なので除外の対象にせず、外部コマンドタブで編集する（`SETTINGS_FIELDS` には登録しない）。`endpoints.*` は enterprise の接続先の上書きで、`deployment_key` と `trace_upload_credentials` に秘密情報を含むため、登録を保留する。
- **Codex**: `config_server.*`（管理者用）と、`requirements.toml` の全キー（別ファイルなので §2 にも該当する。`unsafe_enforce_sqlite_journal_mode` を含み、`config.schema.json` には存在しない）、ソースの説明が `Requirements-only gate` の `features.*`、リファレンスに利用者の無効化は無視され管理要件でだけ無効にできるとある `features.unified_exec`。それ以外の `config.toml` のキーは個人設定として扱う。

## 4. 型の割り当て

- 単一スカラー（boolean / string / number / 厳密な列挙値）→ 編集可能型（`boolean` / `string` / `number` / `enum`。Claude の `env` 内フラグは `envFlag`）。
- 配列・マップ・動的テーブル・union・ハイブリッド（boolean | table）→ `directEdit`（一覧表示のみ。値欄に「ファイルを直接編集」を表示）。ただし OpenCode の `model` は文字列とオブジェクトの union だが、文字列表記で表の編集対象にする（オブジェクト形式は文字列表記で表示し、変更して保存したときだけ文字列で上書きする）。
- ハイブリッド（boolean | table）型は、サブスカラーを個別行に分解しない（親を `directEdit` にする）。分解すると boolean と table の書き込みが競合しうるため。例: Codex の `features.network_proxy` / `approval_policy` / `tools.web_search`、Claude の `attribution`（object | false）。
- 親オブジェクトを `directEdit` で登録済みなら、その配下キーは登録済み扱いとし、個別追加しない。動的なテーブルの行（`apps.<id>`、`agents.<name>` など）と、公式が固定名で定義するキーの編集可能な行（`apps._default.enabled`、`agents.enabled` など）は別のキーなので併存できる。
- 単一スカラーでも、親のテーブルが空のときとテーブルがないときで CLI の動作が変わるキーは `directEdit` にする。表から未設定に戻すと空のテーブルが残り、行は未設定と表示するのに CLI は別の値として読むため。例: Codex の `plugins._default.enabled`（空の `[plugins._default]` は `enabled = true`、テーブルがなければ提供元やアカウントの設定に従う）。
- 同じ設定画面のタブや別の画面で編集できるキーは、型を `directEdit` のまま `linkTab`（同じ画面のタブの ID）か `linkRoute`（別の画面のルート）を付けたリンク行にする。値欄には編集先へのリンクを表示し、テーブル保存の対象にしない。i18n は他の項目と同じく必須で、`linkTab` はそのタブの見出し（`profile.tab.<linkTab>`）、`linkRoute` はリンクの文言（`profile.link.<key>`）も両言語で用意する。機能のスイッチ（Claude の `disableAllHooks`、`outputStyle`、Codex の `features.hooks`、Grok の `workflows.enabled` など）はタブがあっても編集可能型のまま残す。
- 文字列の列挙値は、厳密な列挙値なら `string` 型の `choices` のセレクト。モデル ID・テーマ・プロバイダ ID など拡張余地のある値は `allowCustom: true` を付ける。
- 型が混在する固定候補から 1 つを選ぶ単一スカラー（例: Grok の `features.telemetry` の `true` / `"session_metrics"` / `false` / `"off"`）は `enum` 型にする。`enumChoices` に候補ごとの値（型付き）と `labelKey` を並べ、i18n に `field.<key>.choice.<labelKey>` の文言を両言語で用意する。
- 値の制約が公式で定まっている場合は宣言する。number は `integer`（整数のみ）・`min` / `max`（範囲）・`exclusiveMin`（`min` を含めない。例: 0 より大きく 1 以下）、string は `pattern`（形式。u フラグの正規表現）。制約に合わない値は丸めずに保存を拒否するため、公式の記述より狭い制約は付けない。
- 既定値は、公式で固定既定を確認できた場合のみ `defaultOn` / `defaultValue` を宣言する。環境依存・モデル依存・未記載の項目は宣言しない。

## 5. 廃止（削除）の条件

- 公式のリファレンス／スキーマ／ソースに存在しない（廃止済み・誤登録）。
- マネージド専用と判明した（§3）。
- 公開中の CLI が読まない（OpenCode のようにスキーマと CLI の実装が食い違う場合は §7、Agy のスキーマの説明が `Not read from settings.json` のキー）。編集先が別のファイルにあるキーは、削除せずリンク行にする（§4。Agy の `hooks`）。

設定画面のグループは `SETTINGS_FIELDS` で最初に現れた順に表示されるため、グループの並びは `SETTINGS_FIELDS` 内の項目の位置で決まる。削除で項目が 1 つも無くなったグループは、i18n のグループラベル（`settings.group.<group>`）も両言語から削除する。

## 6. 実装手順（追加・削除ともに）

1. 対象 agent の `shared/agents/<agent>/constants.ts` の `SETTINGS_FIELDS` を編集する。
2. i18n を日本語・英語の両方で編集する（`renderer/i18n/locales/<lang>/<agent>.ts` の `field.<key>` に、項目固有の短い label と desc）。`directEdit` 項目も i18n を必須とし、キーだけのタイトルや汎用説明へのフォールバックは使わない。i18n を欠くと UI にキー文字列がそのまま表示される。
3. `yarn lint`（`tsc --noEmit`）を通す。i18n の欠落は型エラーにならないため、追加した各キーが `constants.ts`・`ja`・`en` の 3 箇所すべてに揃っているかを grep 等で確認する。
4. `CHANGELOG.md` にエージェント別の増減件数で記載する（個々の項目名は不要）。例: `Added — Claude +5 / Codex +10 …`、`Removed — Claude -1 / …`。件数は、直前のリリース（コミット済みの HEAD）と現在の `SETTINGS_FIELDS` の `key` の集合を比べて数える（`key` を変えた項目は削除 1 件・追加 1 件、型や説明だけを変えた項目は数えない）。既存の行とリンク行の間の変換は `key` が変わらないので、追加にも削除にも数えない。HEAD にない `key` の行は、リンク行でも追加 1 件と数える。

## 7. 検証上の注意

- 巨大な公式ページ（特に Claude の `settings-reference.md`）は、取得ツールのサマライザがページ後半を取得できず、存在しないキーを捏造して返すことがある。逐語取得・アルファベット範囲の分割取得・キーの個別存在確認で裏取りし、確証が取れないキーは追加しない。存在しないキーの誤登録は、削除漏れよりも有害である。
- OpenCode は OpenCode 2 のソースとスキーマにあるキー名（`snapshots`・`media`・`commands`・`agents`・`experimental.subagent_depth`・`compaction.keep.tokens`・`compaction.buffer` など）で登録し、その存在を確認する。スキーマが受け付けても OpenCode 2 の動作に使われないキー（`share`・`username`・`lsp`）は登録しない。公開スキーマにあっても最新リリースの `packages/core/src/config/normalize.ts` が読まないキーは、リリースされるまで保留する。`instructions` は OpenCode 2 の初期指示に含まれる有効なキーで、配列なのでリンク行（指示ファイルタブ）で登録する。`enterprise`（組織管理）、TUI 専用の `cli.json`、バックグラウンドサービスの `service.json` のキーも対象外とする。`model` のように文字列とオブジェクトの union でも、文字列として編集できるものは編集可能型にし、オブジェクト形式の扱いは `システム仕様.md` の設定画面の記述に従う。`compaction.buffer` は割合の文字列とトークン数の union で、1 つの入力型に収まらないので `directEdit` にする。
- 判断がつかないキーは追加せずに保留し、根拠を添えて §8 に記録する。
