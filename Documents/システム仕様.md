# Agent CLI DevKit システム仕様

## 1. 概要

Agent CLI DevKit は、AI エージェント CLI（Claude Code / Codex CLI / Antigravity CLI / Grok CLI / OpenCode）の開発環境を管理する Electron 製デスクトップアプリケーションである。
UI・内部構造ともに agent を単位としてグループ化し、表示順は Claude / Codex / Agy / Grok / OpenCode とする。画面上の Agy グループは Agy CLI（Antigravity CLI）のみを意味し、別製品の Agy および Antigravity IDE とは区別する。

- プロジェクト名: `agent_cli_devkit`
- 設定ファイルディレクトリ: `~/.agent_cli_devkit`（`src/shared/constants.ts` の `APP_DIR_NAME`。テーマ・言語を `settings.json` として保存する）
- 実行ファイル名: `agent_cli_devkit`
- 配布ファイル名: `agent-cli-devkit-<version>-<os>-<arch>`
- renderer へ公開するグローバル API: `window.agentCliDevkit`

## 2. アーキテクチャ

### 2.1 設計原則

1. **agent 別ファイル分離** — 各 agent の実装が同一ファイルに混在しないよう、層ごとに `claude/` / `codex/` / `agy/` / `grok/` / `opencode/` ディレクトリへ分割する。複数 agent を同時に参照してよいのは「登録ポイント」（registry・合成ファイル）のみ。
2. **共通化** — agent に依存しない処理（WSL 検出、ホームディレクトリのファイル操作、git 実行、サイズ計測、frontmatter/YAML/TOML 編集）は共通モジュールに置き、各 agent から利用する。
3. **拡張容易性** — 新しい agent CLI は「agent 別ディレクトリを追加し、各層の登録ポイントに 1 行追加する」だけで組み込める（§6 参照）。

### 2.3 プロセス構成と IPC

- メインプロセス起動時に `registerIpcHandlers()`（`src/main/ipc/index.ts`）が `WslDetector` と `AgentCliRunner` を 1 つずつ生成し、各 agent のマネージャに注入して IPC ハンドラを登録する。
- **`AgentCliRunner`（CLI のヘッドレス実行）** — 作業ディレクトリをホームに固定して CLI を実行する。アプリ自身の作業ディレクトリが CLI のプロジェクト判定（設定スコープの自動選択など）に影響しないようにするため。
    - native: 実行ファイルを Windows は `where.exe`、それ以外は `command -v` で解決し、`cwd` をホームにして直接起動する。Windows は候補のうち拡張子 `.exe` / `.cmd` / `.bat` を持つ最初のものを使い、`.cmd` / `.bat` は `cmd.exe /d /v:off /s /c` 経由で実行する。cmd.exe は引用符の内側でも `%VAR%` を展開するため、この経路では `%` を含む引数を実行せずに拒否する（機械コード `invalid-argument-percent`。画面では理由を表示する）。Windows 付属のコマンド（cmd.exe / where.exe / taskkill.exe / wsl.exe）は、`src/main/utils/system32Command.ts` で求めた System32 の絶対パスで起動する（`AgentCliRunner` と `WslDetector` で共通）。
    - WSL: `wsl.exe -d <distro> --exec bash -lc "<WSL_CLI_PATH_SETUP>; cd ~ || exit 1; <CLI の解決>; …"` で実行する。`--exec` で distro の既定シェルを介さないため、引数の `$` や引用符は bash だけが解釈する。CLI は `type -aP` で PATH 順に探し、Windows 側のドライブ（`/mnt/` 配下）にある同名のコマンドを除いた最初のものを使う（見つからなければ終了コード 127）。引数はシングルクォートで囲んで渡す。
    - 引数の検査: すべての引数を `validateArg`（1〜2048 文字、二重引用符・制御文字を含まない）で検査し、通らなければ実行しない。プラグインの変更操作は加えて `validateOperand`（空白だけの値と、オプションとして解釈される `-` 始まりの値を拒否）で検査する。
    - タイムアウト（既定 60 秒）と出力上限（stdout と stderr の合計 32 MB）を超えたら、起動したプロセスを子孫ごと止め（Windows は `taskkill /T /F`）、止めた理由を stderr の先頭に入れて返す。プロセスの終了後は出力の終端を最大 2 秒だけ待つ。
    - CLI の有無はキャッシュする。`checkCli` は `<cli> --version` を実行して確かめ、`resolveCli` は CLI 本体を実行せず PATH の解決だけで確かめる（WSL は実行時と同じ PATH・同じ規則で解決する）。`invalidate` でキャッシュを破棄する。
- WSL での CLI の実行と存在確認（`AgentCliRunner.run` / `resolveCli`、OpenCode の `OPENCODE_WSL_CLI_TEST`。いずれも `src/shared/agents/wsl.ts` の `wslFindCliScript` / `wslCliTest` の同じ規則に従い、`/mnt/` 配下の同名コマンドは使わない）は、前に `WSL_CLI_PATH_SETUP`（`src/shared/agents/wsl.ts`）を置いて同じ PATH を見る。これは `~/.bun/bin`・`~/.opencode/bin`・`~/.local/bin` のうち PATH に無いものを PATH の**末尾**に加える（`bash -lc` は非対話シェルのため、インストーラが `.bashrc` に加えた PATH の追記が効かない）。末尾に加えるため、PATH で既に解決できるコマンドの解決先は変わらない。wsl.exe の引数として渡すため二重引用符を使わない。
- `WslDetector` の distro 内実行は、コマンドを `wsl.exe -d <distro> --exec bash -lc <command>`（`runInDistro`。判定コマンドもこの形で実行する）で、長いスクリプトを標準入力から `bash -l -s` へ渡す形（`runScriptInDistro`、前後の目印を必須とする `runMarkedScriptInDistro`）で行う。いずれも distro の既定シェルを介さない。ログインシェルの出力は目印で取り除く（§3.9）。
- 設定ファイル（JSON / JSONC / TOML）は、先頭の UTF-8 BOM を除いてから解釈する。保存は BOM を除いた内容に対して差分を適用し、ファイルの BOM を見つけたときの形のまま書き戻す。直接編集で入力されたテキストの先頭の BOM は除く（BOM の規則は §3.9）。空または空白だけのファイルは空の設定として扱い、テーブル編集で保存すると初期内容（OpenCode は `$schema` を含むオブジェクト）から書き始める。
- preload は `sandbox: false`（`contextIsolation: true` は維持）で動作し、agent 別ブリッジファイル（`preload/agents/*.ts`）を require 合成して `window.agentCliDevkit` を公開する。sandbox を無効化しているのは preload を agent 別ファイルに分割するためで、shared の定数・型を preload から直接 import できる利点もある。
- IPC チャンネルは agent プレフィックスで名前空間化されている:
    - Claude: `claude-desktop:*` / `claude-code:*` / `claude-cleanup:*` / `claude-asset:*` / `claude-settings:*` / `claude-plugin:*`
    - Codex: `codex-mcp:*` / `codex-asset:*` / `codex-cleanup:*` / `codex-config:*` / `codex-plugin:*`
    - Agy: `agy-mcp:*` / `agy-asset:*` / `agy-cleanup:*` / `agy-settings:*` / `agy-plugin:*`
    - Grok: `grok-mcp:*` / `grok-asset:*` / `grok-cleanup:*` / `grok-config:*` / `grok-plugin:*`
    - OpenCode: `opencode-mcp:*` / `opencode-asset:*` / `opencode-cleanup:*` / `opencode-settings:*` / `opencode-plugin:*`
    - プロファイル設定: `<agentId>-profile:*`（全 agent 共通の形。§3.8）
    - 共通: `window:*` / `system:*` / `app-settings:*` / `updater:*` / `main:console`

**Claude クリーンアップの一時物:**

- 一時ルート: OS の一時フォルダ（Windows は `<tmpdir>\claude`、Linux / WSL は `/tmp/claude-<uid>`、macOS は `$TMPDIR/claude-<uid>`）と、`CLAUDE_CODE_TMPDIR`（プロセス環境変数と `~/.claude/settings.json` の `env`）が指す一時フォルダの下にある同名のディレクトリ。リンクではない実行ユーザー所有のものだけを扱う。
- セッションの作業フォルダ: 一時ルート直下の `<プロジェクト名>/<セッション ID>`。`<プロジェクト名>` は作業フォルダの絶対パスを符号化した名前（英数字以外は `-`）で、`~/.claude/projects/<プロジェクト名>` と同名のものを同じプロジェクトとして対応付ける（Windows は大文字小文字を区別しない）。削除後に空になった `<プロジェクト名>` ディレクトリも削除する。
- MCP ログ: Windows は `%LOCALAPPDATA%\claude-cli-nodejs\Cache\<プロジェクト名>`、macOS は `~/Library/Caches/claude-cli-nodejs/<プロジェクト名>`、Linux / WSL は `$XDG_CACHE_HOME`（未設定なら `~/.cache`）の `claude-cli-nodejs/<プロジェクト名>`。
- bash-edit-diff: 一時ルートの `bash-edit-diff/<セッション ID の wyhash64（10 進）>-<数値>-<16 桁の 16 進>`。会話履歴の `<セッション ID>.jsonl` / `<セッション ID>` ディレクトリと作業フォルダのセッション ID から wyhash64（`main/utils/wyhash.ts`）を求めて照合し、一致したプロジェクトに含める。一致しないものは temp-bash-edit-diff の候補にする。
- temp-bundled-skills: 一時ルートの `bundled-skills/<バージョン>`。
- 実行中のセッション: プロセスは調べず、次の 2 つを実行中として扱う。
    - `~/.claude/sessions/<pid>.json` に登録されたセッション（`sessionId` / `version` / `cwd` / `name`）。登録した環境（`pidDomain` の OS・ホスト名）は問わず、すべての登録を実行中とする。WSL 環境では Windows 側の `~/.claude/sessions` の登録も加える。異常終了などで終了済みのセッションの登録が残っている場合も実行中と判定されるため、下記「使用中と判定したセッションの削除」で利用者が個別に削除を承認できる。
    - 登録の無いセッションのうち、会話記録（`<セッション ID>.jsonl` または `<セッション ID>/`）が 10 分以内に更新されたもの（未来の日時を含む）。登録を書かないセッションを、会話記録を書き続けることから検出する安全網。
- 会話履歴の扱い（プロジェクトごと）:
    - free（実行中のセッションが無い）: 行のエントリ（`memory/` を除く）をすべて削除の対象にする。
    - partial（実行中のセッションがある。登録の `cwd` が指すプロジェクトを含む）: 使用中の可能性がある行として、承認されない限り削除しない。そのセッションの会話記録とリンクの数を使用中の可能性があるものの件数として数える。
    - locked（実行中のセッションが分からない、または会話履歴を一覧できない）: 使用中の可能性があるプロジェクトとして、承認されない限り削除しない（会話履歴全体を 1 件と数える）。登録を一覧できない・読めない・解析できないものがあって実行中のセッションが分からない場合は、セッション単位の一時物（作業フォルダ・bash-edit-diff・MCP ログ・bundled-skills）もすべて使用中として扱う。
- 一時物の使用中の判定: 実行中のセッションの作業フォルダと bash-edit-diff、実行中のセッションがあるプロジェクトの MCP ログは使用中の可能性があるものとし、それを含むプロジェクトは承認されない限り削除しない。登録されたバージョンの bundled-skills は削除しない。画面では、行の件数・サイズを、削除を承認すれば消える全体（`memory/` を除くエントリとすべての一時物）で集計し、残すものの件数（下記「使用中の可能性あり」の表示）と、会話履歴が無いプロジェクトの「会話履歴なし（一時物のみ）」を添える。使用中の bundled-skills / bash-edit-diff は「使用中のため対象外」と表示して選択できなくする。削除後の通知と削除できなかったパスの報告は、下記「クリーンアップの使用中判定（共通基盤）」の全エージェント共通の扱いに従う。
- 使用中の可能性があるプロジェクトの削除: プロセスを調べないため使用中の判定は推定であり、終了済みのセッションの登録が残っていても使用中と判定される。そこで、プロジェクトの子要素は残すものの根拠にしたセッションを `CleanupChild.inUseSessions`（識別子・根拠・登録の `name`）として返し、削除の確認でプロジェクトごとに削除するかを問い合わせる。識別子は小文字のセッション ID（セッション ID の無い登録は登録ファイル名から `pid:<pid>`）で、実行中のセッションが分からない（locked）プロジェクトは全セッションを表す `*` の 1 件にする（根拠は `unknown`。画面は根拠で「すべてのセッション」と表示する）。根拠は `registered`（実行中として登録あり）/ `recent`（10 分以内に更新）/ `unknown`（判定できない）。画面では、`inUseSessions` のあるプロジェクトに「使用中の可能性あり（会話記録・一時物など N 件）」を表示し、削除できるものが無くても選択できる。削除の確認ダイアログには、選択したプロジェクト（projects 全体の選択ではすべてのプロジェクト）のうち `inUseSessions` のあるものだけを、根拠のセッションを添えてチェックボックス付きで並べる（既定は未チェック。注意表示の無いプロジェクトは問い合わせない）。チェックしたプロジェクトは `CleanupSelection.approvedChildren` で渡し、main 側は実行中のセッションが無いものとして構成を調べ直し、会話記録と一時物をすべて削除する（`memory/` は残す）。チェックしないプロジェクトは削除の対象にしない。
- 削除できなかったパスの報告: 削除は `CleanupProbe.removeReporting` で行い、OS のファイルロック（他のプログラムが開いているファイル）などで消せないものを飛ばして残りを削除し、対象ごとに残ったパスを返す（Linux / WSL には削除を妨げる OS のファイルロックが無いため、主に Windows で他のプログラムが開いているファイルが残る）。ディレクトリは配下に残った末端（ファイル・リンク・空のディレクトリ、別のファイルシステムのディレクトリ）を並べ、特定できない場合は対象自体のパスにする（native は `removeTreeBestEffort` の `failed`、WSL は `rm -rf` 後の `find -P -xdev`）。Claude クリーンアップは残ったパスを `CleanupEnvReport.failedPaths` に集め、画面は削除の最後に「削除できなかったファイル」ダイアログで一覧表示する（まとめてコピー可能）。

### 3.5 OpenCode グループ

対象は `opencode --version` が成功して 2.x を返す OpenCode 2 の公式グローバル/XDG 領域だけである。

導入判定（`openCodeCli.ts` の `openCodeCliAvailable`）は `AgentCliRunner.checkCli` で環境ごとに `opencode --version` を実行する。終了コードが 0 で、標準出力の最初の行が `opencode v2.0.29`・`v2.0.29`・`2.0.29` などの 2.x のバージョン表記なら対象にする（プレリリースとビルド情報を含む）。1.x・3.x・空の出力・不正な出力・実行失敗は対象外にする。バージョン確認によって OpenCode のログやフォルダーが作成される場合がある。同じ判定を通した環境で `opencode plugin add`・`opencode session delete`・`opencode api` を実行する。

native のコマンド解決は `AgentCliRunner.resolveNativePath` が Windows では `where.exe`、macOS・Linux では `command -v` を使う。macOS・Linux では `nativeCliEnvironment` が継承した PATH の末尾へ `${BUN_INSTALL:-~/.bun}/bin`・`~/.opencode/bin`・`~/.local/bin`・`/opt/homebrew/bin`・`/usr/local/bin` を重複なく加える。解決と実行の両方に同じ環境を渡し、子プロセスのインタープリタも同じ PATH で探す。シェルの初期化ファイルは実行しない。WSL の候補は `OPENCODE_WSL_CLI_TEST` が成功する distro、つまり §2.3 の PATH 補完と `/mnt/` 配下を除く規則で `opencode` が解決できる distro とし、候補ごとに `openCodeCliAvailable` でバージョンを確認する。共通の Agent/Skill・設定・クリーンアップ管理は `wslAvailable` オプションで同じ判定を適用する。

判定結果は `AgentCliRunner`（コマンド解決とバージョン確認）と `WslDetector`（判定コマンドごとの distro 一覧）が環境ごとにキャッシュする。各画面の「再取得」（`opencode-*:get-environments` の `refresh=true`）で両者の `invalidate` を呼び、検出し直す（画面を開いたときは破棄しない）。標準の導入先への導入・削除は再起動せずに反映できる。Windows の `where.exe` は起動時の PATH を使うため、新しいフォルダーが PATH に追加された場合はアプリの再起動が必要になる。

OpenCode はバージョン確認、プラグイン導入、セッション履歴の一覧・削除で実行する。クリーンアップの projects の行はデータベースを直接扱い、OpenCode を実行しない（§3.10）。セッション履歴の一覧は、データベース（`~/.local/share/opencode/opencode.db`）がある環境でクリーンアップ候補を走査するときに取得する。対象の環境が無いときは MCP・Agent/Skill・Plugin・設定・クリーンアップの各画面が `opencode.noEnvironment` の OS に依存しない案内を表示する（共通ビューは `nativeAvailable` オプションで native の有無を差し替え、他 agent は常に native を表示する）。OpenCode が互換読み込みする `~/.claude` / `~/.agents` と workspace の `.opencode` は管理しない。XDG 領域は全 OS でホーム相対（`~/.config` / `~/.cache` / `~/.local/share` / `~/.local/state`）として扱い、`XDG_*_HOME` 環境変数による変更先は考慮しない。

**グローバル設定ファイル:** `~/.config/opencode` の `opencode.json` / `opencode.jsonc`（`openCodeConfigFile.ts`）。どちらも無ければ `opencode.json` を作成する。OpenCode は両方のファイルを読み込み、同じ値は `opencode.jsonc` を優先する。

- MCP・Plugin: 両方のファイルを読み、一覧に定義のあるファイルを `definedIn` で返す（MCP の実効の値は後のファイルの定義）。どれかのファイルを読めなければ何も書かない。無効化は定義のあるすべてのファイルから要素を除き（1 つでも残ると有効なままになるため）、有効化は記録した元のファイルへ戻す。記録が無ければ、また新しく追加する内容は、存在する最初のファイル（両方あれば `opencode.json`）に書く（`resolveOpenCodeConfigRel`。`opencode mcp add --global` / `opencode plugin add` が書き込む先と同じ）。
- 設定とプロファイル設定のタブ: 存在する最後のファイル（両方あれば、OpenCode が値を優先する `opencode.jsonc`）を表示・編集する（`resolveOpenCodeSettingsRel`）。両方あるときは、`opencode.json` だけにある設定も OpenCode では有効だが表には出ない旨を、表の上に注記する（`fileNotice` = `notice.jsonAlsoExists`。タブは `opencode.profile.bothConfigFiles`）。

### 3.6 共通機能

- **ダッシュボード** — agent ごとに Claude / Codex / Agy / Grok / OpenCode の固定順でアコーディオンを表示し、配下に全機能のカードを並べる。アコーディオンは排他展開（1 つ開くと他が閉じる）で、最後の展開状態を localStorage へ保存し次回起動時に復元する（初回は先頭グループを展開）。グループ名は `AgentModule.labelKey` の文言で表示し、Agy と OpenCode の見出しは `dashboardLabelKey` の文言（「Agy（Antigravity CLI）」、英語は「Agy (Antigravity CLI)」、「OpenCode 2」）で補足する。カードはアイコンを左・テキストを右に置く横並びのコンパクトレイアウト。`renderer/agents/index.ts` の registry から自動生成。
- **タイトルバー** — ダッシュボードアイコンに続き、agent グループの代表ボタンを Claude / Codex / Agy / Grok / OpenCode の順で表示するアコーディオン方式。代表ボタンをクリックするとそのグループの機能アイコン（通常より一回り小さい 22px アイコン）が展開され、別グループを展開すると先に開いていたグループは自動で閉じる（同じボタンの再クリックで閉じる）。画面遷移時は遷移先の機能が属するグループを自動展開する。右側にはアプリ設定アイコン（ラベルなし）とバーガーメニューを置く。幅が足りないとき（最小幅の 800 px で Claude のグループを展開したときなど）は、ダッシュボードアイコンと agent グループの範囲だけを横にスクロールし（スクロールバーは出さず、ホイールで動く。展開したグループは見える位置へ動かす）、アプリ名は 1 行のまま省略する。省略している間だけ、名前はホバーでバージョンを含む全体をツールチップに表示し、ウィンドウのドラッグ領域から外れる（`ResizeObserver` で省略の有無を見る）。バーガーメニューのサブメニューはメニューが開いている間だけ表示し、メニューを閉じたときと画面遷移で消す。閉じるアニメーション中に行の上へポインターが乗っても開かない。アプリ設定、バーガーメニュー、ウィンドウの操作ボタンは縮めず、文書全体は横にスクロールしない。バーガーメニューは「ダッシュボード / agent グループ（ホバーで機能一覧をカスケード表示する 2 階層メニュー。右側に展開し、収まらない場合は自動で左へ反転）/ アプリ設定 / 終了」で構成する。
- **共通の見た目** — ボタンとタブのラベルはテーマの `typography.button.textTransform: none` で全画面とも書いた表記のまま表示する。`CssBaseline` の `enableColorScheme` でスクロールバーをテーマの明暗に合わせる。長い文を持つチップは `renderer/utils/wrappingChip.ts` の `WRAPPING_CHIP_SX` で折り返す。設定の表は `tableLayout: fixed` で項目の列に長い語の折り返しを許し、最小幅でも横スクロールを出さない。Agent・Skill の一覧は `fitColumnLimit` が名前の列の上限を抑えて、残り幅を使う説明の列の幅を確保する。
- **アプリ設定** — `/app-settings` でテーマ（ライト/ダーク）と言語（日本語/英語）を編集する。編集値はドラフトとして保持し、「保存」を押した時点でアプリへ反映して `~/.agent_cli_devkit/settings.json` へ永続化する。保存値がない初回起動時は OS のテーマ・言語設定を引き継ぐ。
- **自動アップデート** — GitHub Releases を対象に electron-updater でチェック/ダウンロード/適用。
- **WSL 対応** — Windows では WSL distro を検出し、対象 CLI が導入された distro を各機能の管理対象として表示。すべての機能を distro の中のスクリプトで動かすので、UNC に届かなくても同じように使える（§3.9）。OS のプロセスへパスを渡す必要があるファイルマネージャーでの表示だけは `\\wsl.localhost\` / `\\wsl$\` の UNC が要り、届かないときは行のアイコンを無効にして理由を表示する（`AssetListReport.revealUnavailable`、`FileCollectionReport.capabilities.reveal`）。
- **Agent・Skill の ZIP ダウンロード** — 既定ファイル名は `<kind>_<agent>[-<distro>][_<エントリ名>].zip`。種別（skills / agents）を先頭に置き、ファイル一覧で種別ごとにまとまるようにする（例: skills_claude.zip / agents_grok-Ubuntu-24.04.zip）。選択が 1 件だけの場合は末尾にその名前を付ける（例: skills_claude_my-skill.zip / agents_grok-Ubuntu-24.04_agent-a.zip）。エントリ名は relPath の末尾セグメントから拡張子を除き、ファイル名に使えない文字を `_` に置換して 60 文字までに切り詰める（`common/assets/archiveFileName.ts` の `assetArchiveFileName`）。ZIP 内の各ファイルのタイムスタンプは元ファイルの更新日時が保持される（archiver が stat の mtime を使う）。ZIP のタイムスタンプはローカル時刻で記録する（archiver の `forceLocalTime: true`。既定の UTC 記録ではエクスプローラや展開時にタイムゾーン分ずれるため）。archiver は渡したオプションオブジェクトへ既定値を直接書き込むため、共通オプションは定数ではなく `zipArchiveOptions()` で都度生成する。
- **Agent・Skill 取り込み時の更新日時の引き継ぎ** — アップロードで配置したファイルの更新日時は、取り込み元の日時を引き継ぐ（アップロード日にしない）。ZIP は各エントリに記録された日時を展開後のファイル（およびディレクトリ）へ適用し、md・ファイル単体は選択した元ファイルの mtime を適用する。ZIP のタイムスタンプは MS-DOS 形式（2 秒粒度・ローカル時刻）のため、ZIP 経由では最大 2 秒の誤差が生じうる。公式スキルのインポート（Claude / Codex）も同じ展開経路のため、取得したリポジトリ内ファイルの日時を引き継ぐ。日時の適用は付加的な処理として扱い、失敗しても取り込み自体は成功とする（警告ログのみ）。
- **Agent・Skill の取り込み（作業フォルダ経由）** — アップロード（ZIP・md・TOML）と公式スキルのインポートは、取り込み先の外（実体の親フォルダー）に隠しの作業フォルダ（`.asset-upload-XXXXXX`）を作って内容を書き出し、すべて書き出せてから取り込み対象を所定の場所へ移す（`common/assets/stagedInstall.ts` の `installFiles`。native は `installStaged`、WSL は `HomeFs.installFilesInDistro` が同じ手順を distro のスクリプトで行う）。同名の既存の対象は、上書きを確認したもの（リンクではないもの）だけを作業フォルダへ退避して置き換え、すべて移し終えてから退避分を削除する。書き出し・移動に失敗した場合と、上書きを確認していない既存の対象があった場合は、移したものを取り除いて退避分を戻し、取り込み前の状態にしてから失敗を返す（戻しきれなかった場合は作業フォルダを残してログに記録する）。取り込みの内容は `StagedFile` の一覧にしてから渡す（`stagedFilesOfArchive`）。WSL は本文を base64 のヒアドキュメントで作業フォルダへ送り（32 MiB ごとのスクリプトに分ける）、確定のスクリプトで sha256 を確かめてから移す。送る途中で失敗すれば作業フォルダを消し、既存の対象に触らない。ZIP のダウンロードも同様に、WSL は distro の中で一覧し（`buildArchiveListScript`）、本文を 48 MiB ごとのスクリプトで読む（これより大きなファイルは分けて読み、全体の sha256 を確かめる）。配下のリンクはリンクのまま ZIP に入れる。環境のファイルに届かない場合（WSL のホームを解決できない）だけ `unavailable` を返す（`HomeFs.isReachable`）。
- **ZIP エントリ名の正規化** — ZIP の各エントリ名は、区切りの `\` を `/` にそろえ、空のセグメントと `.` のセグメント（先頭の `./` など）を取り除いた相対パスとして扱う（`common/fs/archiveEntryPath.ts`）。絶対パス・ドライブ文字で始まる名前と、安全でないセグメント（空白だけ、`..` を含む、`/`・`\`・`:`・制御文字を含む、末尾がドットか空白）を含む名前が 1 つでもあれば、ZIP 全体を `invalid-archive` として受け付けない。取り込み対象（トップレベルのディレクトリ・ファイル）と同名の既存の確認も、正規化したパスで行う。
- **MCP 管理（共通レイアウト）** — 全 agent の MCP 画面は同一レイアウト。ヘッダーに設定ファイルと無効化ファイルの両パスを表示し、有効/無効の 2 テーブル（列: ドラッグハンドル / サーバー名 / 操作トグル / コマンド / 引数）を `tableLayout: fixed` で画面幅比率から配分する（引数列が最大）。長い値は省略（…）せず自動改行し、行のドラッグ&ドロップで並べ替える。無効化はフラグ書き換えではなく、エントリ/ブロックごと各 agent の無効化ファイルへ退避する方式で統一する。
- **クリーンアップの使用中判定（共通基盤）** — ホーム外（OS の一時フォルダなど）や使用中かもしれない一時物を含む候補は、プロセスを調べず、ロックの保持・書き込みオープンの可否・ファイルの中身・更新日時だけで判定する。`AgentCleanupManager` は候補ごとに `resolvers`（`CleanupResolver`：子要素を絶対パスで解決し、`excluded` に `in-use`（使用中）/ `ineligible`（条件外）を付ける）、`handlers`（CLI で消す候補。`CleanupHandler`。走査のたびに `listChildren` で子要素を一覧し（`listHandled`。失敗はログに記録して対象なしとする）、リゾルバと同じく削除できる子要素の件数・サイズの候補にする。CLI の実行は副作用を伴うため、ハンドラーは消す対象が無いと分かる環境（CLI やデータが無い環境）では CLI を実行せずに空を返す。候補全体の削除はハンドラーが削除時に一覧し直してから消す）、`lockFile`（ロックが保持されている間は対象外にする単一ファイル）を受け付ける。判定と削除は `CleanupProbe`（native / WSL。WSL は `WslDetector.runScriptInDistro` で distro 内のスクリプトを実行）が行い、配下のシンボリックリンク・ジャンクションは辿らず、判定に失敗したときは削除しない側に倒す。リゾルバは削除の直前にも呼び直して再判定する。使用中の子要素は画面に「使用中のため対象外」と表示して選択できなくし、条件外のもの（日時が新しいなど）は画面に出さない。ただし、プロセスを調べない推定で使用中の可能性があるとしたもの（`CleanupChild.inUseSessions` のあるもの。Claude のプロジェクトと OpenCode のセッション）は「使用中の可能性あり」と表示して選択でき、削除の確認ダイアログで項目ごとに削除するかを問い合わせ（既定は未チェック。注意表示の無いものは問い合わせない）、チェックしたものだけを `CleanupSelection.approvedChildren`（候補キー → 子要素名）で渡して削除する。承認しなかったものは個別選択から外し、候補全体の選択でも削除しない（共通部品 `renderer/components/agent/CleanupDeleteDialogs`）。展開可能な候補は、削除できるファイルが 0 件でも子要素（中身が 0 件のディレクトリを含む）があれば表示する（`isVisibleCandidate`）。削除後の通知は、削除しようとして削除できなかったもの（`CleanupEnvReport.skipped`・`failedPaths`、「その他のツール」の失敗）があれば「一部を削除できませんでした」（警告）、それ以外は完了とし、使用中のため削除の対象にしなかったもの（候補全体の削除で選択できない使用中の子要素、承認しなかったもの）は報告しない（`deleteResolvedChildren` は names='all' のとき使用中のものを報告しない）。OS のファイルロックなどで削除できずに残ったパスは `CleanupEnvReport.failedPaths` で返し、画面は削除の最後に「削除できなかったファイル」ダイアログで一覧表示する（全エージェント共通。ホーム相対パスの削除は `removeHomeTargets`）。削除のしかたは次項の共通の削除と同じ。
- **ディレクトリの削除（共通）** — クリーンアップ、Agent・Skill の削除、プラグインの削除、取り込みの巻き戻しでのディレクトリ削除は、使用中（ロック）などで消せないものを残し、消せるものだけを削除して、すべて削除できたかを返す（best-effort）。シンボリックリンク・ジャンクションは辿らず、リンク先には触れない（配下のリンクはリンク自体だけを外し、起点自体がリンクなら何も削除しない）。native は `common/fs/removeTreeBestEffort.ts` の `removeTreeBestEffort` がエントリ単位で削除し、`failed` を渡すと消せずに残したパスを集める（Windows のジャンクション・マウントポイントもリンクとして扱い、起点と別のファイルシステムのディレクトリには降りない。読み取り専用で消せないファイルは属性を外して再試行する）。WSL の環境（`HomeFs` / `CleanupProbe`）は distro 内の `rm -rf`（GNU coreutils なら `--one-file-system` 付き）で削除する。
- **Agent・Skill 一覧の検索** — 各 agent のエージェントタブとスキルタブでは、名前または説明による絞り込みに対応する。検索語は空白区切り（順不同）の AND 条件とし、全検索語が名前内、または全検索語が説明内に含まれる項目を表示する。大文字小文字および全角半角の違いは区別しない。検索条件と一括操作の対象はタブごとに独立し、一括操作は現在の検索結果に表示されている選択項目だけに適用する。
- **Agent・Skill 一覧のファイルマネージャー表示** — 名前の右にある外部リンクアイコンから、エージェントは対象ファイルを OS 標準のファイルマネージャー内で選択表示し、スキルは対象ディレクトリを開く。native はホスト OS の絶対パス、WSL は `HomeFs.resolveRealPath` が解決した UNC パスを `<agent>-asset:reveal-entry` で Electron の `shell` へ渡す。main 側で種別と相対パスを検証し、管理対象外のパスは開かない。UNC に届かない WSL では一覧に `revealUnavailable` を返し、行のアイコンを無効にして、開けない理由をツールチップに表示する（`common.revealUnavailable`、`AssetEntriesTable` の `revealDisabledReason`）。
- **エージェント一覧の推論レベルと補足情報** — Claude / Codex / Grok のエージェントタブでは（Agy / OpenCode は次項）、モデル列のセル内でモデル名の次の行に推論レベルを「(値)」の小さく控えめな表記で表示する（Claude / Grok は frontmatter の `effort`、Codex は TOML の `model_reasoning_effort`。モデル未指定で推論レベルのみの場合も同じ位置に表示）。説明列の下には、一覧で把握すべき重要な設定だけを「キー: 値」で小さく並べる（最大 2 行で省略し、ツールチップで全項目を表示）。全キーの網羅はせず、能力・権限を変えるものに限る。対象は Claude / Grok が `tools` / `disallowedTools` / `permissionMode`（Grok Build の `AgentDefinition` も同名キーを読む）、Codex が `[features]` で `false` にした機能（`機能名=false` のカンマ区切り。`sandbox_mode` / `mcp_servers` などはカスタムエージェントでは親設定を上書きしないため表示しない）。値が既定値と同じ項目（例: `permissionMode: default`）は明示されていても表示しない。列ごとの指定は `FmColumn` の `effortKey` / `detailKeys`（`renderer/components/assets/assetColumns.tsx`。既定値付きの指定は `DetailKey` の `defaultValue`）で行い、Agy / OpenCode の共通一覧は `AssetManagerView` の `columns`（種別ごとの列構成）で指定する。
- **Agy / OpenCode のエージェント一覧** — 共通一覧（`AssetManagerView`）は `columns`（種別ごとの列構成）を受け取り、両 agent はエージェントタブにモデル列を持つ。Agy は `model`（`inherit` / `flash` / `pro`。推論レベルの公式キーは無い）を表示し、説明列の下に `tools` / `commandExecutionPolicy`（既定 `sandbox` は非表示）/ `mainAgent`・`subagent`（既定 `true` は非表示）を補足表示する。OpenCode はモデル列に `provider/model` を表示し、次の行に推論レベルとしてモデルバリアントを表示する。文字列形式 `provider/model#variant` は `#` 以降をバリアントとし、オブジェクト形式 `model: { providerID, model, variant }` は `providerID/model` をモデル、`variant` をバリアントとして解決する（`renderer/agents/opencode/modelColumn.ts` の `resolveOpenCodeModel`。`FmColumn` の `resolve` で指定）。そのうえで、説明列の下に `mode`（既定 `primary` は非表示）/ `disabled`（既定 `false` は非表示）/ `steps` / `permissions` を補足表示する。`permissions` は `{ action, resource, effect }` の並びのため、`OpenCodeAssetManager` が一覧取得時に「action:resource=effect」のカンマ区切り 1 行へ要約する（ブロック形式の記述が対象）。
- **Claude の同期スキル（`~/.claude/skills/synced`）** — Claude Code は claude.ai のアカウントで有効な Anthropic 提供スキル（`anthropic-skills:` 名前空間。`manifest.json` の `source` は `anthropic` / `anthropic-example`）を `synced/<組織ID>_<ユーザーID>/<スキル名>/SKILL.md` へ起動のたびに同期する（同階層に `manifest.json` / `.last-complete-round`、`synced/` 直下に `.bucket-*` マーカー）。内容は Anthropic 側の配信で上書きされ、利用者が管理する対象ではないため、スキル一覧では `SKILL.md` を持たない `synced/` を一覧から除外する。同期領域の上書き・削除を防ぐため、`synced` と同名になる md アップロードや `synced/` をトップレベルに含む ZIP アップロードは `synced-reserved` として受け付けない。他 agent は CLI の自動配置スキルが管理対象外の場所にある（Codex の `~/.codex/skills/.system`、Grok の `~/.grok/bundled/skills`）ため、同等の扱いは不要。
- **スキル一覧から除外する隠しディレクトリ** — `SKILL.md` を持たない `.` 始まりのディレクトリ（Claude Code が claude.ai の同期で外したスキルを復元用に退避する `skills/.trash/` など）はスキルではないため、Claude / Codex / Grok のスキル一覧に出さない（Agy / OpenCode は `SKILL.md` の無いディレクトリを元から出さない）。`skills/.trash/` はクリーンアップの候補として扱う。
- **Agent・Skill の一覧の走査** — 一覧は `common/assets/assetScan.ts` の `scanFileAssets`（.md / .toml を 1 件とする種別）と `scanDirAssets`（目印のファイルを持つフォルダーを 1 件とする種別）で作る。`HomeFs` の `listTree`（再帰）と `listEntries`（直下）を使い、取り込みの作業フォルダと原子的な書き込みの一時ファイルは出ない。再帰で読む種別（Claude / Codex の agents、OpenCode の agents と agent）の深さの上限は 32（`RECURSIVE_ASSET_MAX_DEPTH`）で、より深いものがあれば `AssetListReport.truncatedDepth` を返して画面に注記する。読めなかったフォルダーがあれば `incomplete` を返す。
- **スキルの探索の深さ** — `scanDirAssets` の `maxLevels` はルート直下を 1 とするフォルダーの階層の上限。OpenCode、Claude、Agy は `SKILL.md` のあるフォルダーの下を読まない。Codex と Grok は `walkBelowEntry` でその下も探し、スキルの中のスキルも行にする。Codex は 6（CLI の `MAX_SCAN_DEPTH`。ルートを 0 として 6 階層目まで読む）、Grok は 6（CLI の `MAX_SKILL_WALK_DEPTH` は 5 で、深さ 5 のフォルダーの子まで調べる。隠しフォルダーも読む）、OpenCode は 6（CLI の `MAX_DEPTH`）、Claude と Agy は 1。OpenCode は `skills/<name>.md` もファイルの行にする。新規の配置はどの agent も 1 階層のまま。Claude はルート直下の目印のないフォルダーを、Codex と Grok はネストしたスキルも見つからないルート直下のフォルダーを「読み込まれない」行として出す。
- **Agent・Skill の行の状態** — `AssetEntry.link` は行とリンクの関係（`self` は行そのものがリンク、`via` は途中のフォルダーがリンク）。`AssetEntry.status` は通常の 1 件ではない行の状態で、`dangling-link`（リンク切れ。CLI に読み込まれない）、`no-entry-file`（目印のないフォルダーと、`hiddenNotLoaded` の種別で CLI が飛ばす `.` で始まるフォルダー。`.` で始まるフォルダーは目印があっても読み込まれない行になる）、`link-folder`（フォルダーへのリンク。配下は別の行）、`link-loop`（既に読んだフォルダーへのリンク）、`refused-name`（`isSafePathSegment` が拒否する名前。操作不可で、配下を読まない）。循環は `HomeFs.realPathKey`（native は realpath、WSL は `readlink -f`）で検出する。削除は `assetEntryOps.removeAssetEntry` で行い、行そのもののリンクはリンクだけを外し、`findLinkBelowRoot` が途中のリンクを見つけたものは削除しない。削除で空になった親フォルダーはルートの手前まで削除する。ダウンロードは `HomeFs.resolveFollowedPath` でリンク先の内容を入れ、リンク切れは含めない。renderer の操作可否は `renderer/utils/assetEntry.ts` にまとめる。
- **複数の読み取り元（Agy / OpenCode）** — `MarkdownAssetManager` の `roots` は種別ごとの読み取り元で、先頭が書き込み先。先頭以外の行の `relPath` は「<識別子>::<相対パス>」の形で、読み取り、表示、ダウンロード、削除はその行のルートに対して行う。`AssetEntry.origin` は由来、`overriddenBy` は同じ名前で優先される読み取り元、`sameNameIn` は優先関係が公式に示されていない同じ名前の読み取り元。Agy のスキルは `antigravity-cli/skills` と `~/.gemini/skills` が `config/skills` より優先され、前の 2 つの間の優先関係は公式に示されていない。OpenCode のエージェントは agent、agents、mode、modes の順に読まれ、後のものがフィールド単位で上書きする。mode と modes の行は mode を primary に固定して表示する。
- **目印のないフォルダーの取り込み（Agy / OpenCode）** — `MarkdownAssetManager` は ZIP のトップレベルのフォルダーのうち目印のファイル（大文字小文字は問わない）を持つものだけを取り込む。すべてのフォルダーに目印がなければ `no-entry-file` で拒否し、一部だけなら `kindCheck: 'warn'` と `kindNames` で確認してから残りを取り込む。
- **アップロードで受け付けるファイル** — `common/assets/inspectedUploads.ts` の `InspectedUploads` が、`inspectUpload` のファイル選択ダイアログで選ばれたパスを環境と種別（一覧は一覧の ID）ごとに覚える。`upload`、`uploadFile`、`uploadMd`、一覧の `upload` は覚えているパスだけを受け付け、それ以外は `invalid-input` を返す。renderer から届く任意のパスは読まない。取り込みが成功すると忘れる。`MarkdownAssetManager`、Claude / Codex / Grok の Asset マネージャー、`FileCollectionManager` が同じ規則を使う。
- **スキルの上書きの確認** — スキルのフォルダーの上書きはフォルダーごと置き換えるので、`inspectUpload` は一覧の行のうち衝突先のフォルダーの中にあるものを `nestedReplaced` で返し（`assetEntryOps.ts` の `nestedReplacedOf`）、上書きの確認ダイアログに警告として並べる。一覧に出ないもの（Claude と Agy で `SKILL.md` のあるフォルダーの下にあるものなど）は含めない。
- **更新ボタン** — Claude / Codex / Grok の Settings、Agent・Skill、MCP、クリーンアップの `getEnvironments` は `refresh` を受け取り、true なら `WslDetector.invalidate` を呼ぶ。Agent・Skill、MCP、クリーンアップの画面は更新中も環境セクションをアンマウントせず、`reloadNonce` の変化で読み直す。Agent・Skill と MCP はタブと検索語を保ち、選択は解除する。クリーンアップは行の展開を保ち、選択は解除する。設定画面は選択中のタブと未保存の編集を保つ（§3.8）。
- **MCP の一覧のデータ** — `JsonMcpManager`、`TomlMcpManager`、`ClaudeCodeManager`、`OpenCodeMcpManager` の `getMCPServers` は `utils/mcpDisplayConfig.ts` で一覧に出す項目（`command`、`args`、`type`、`url`、`serverUrl`）だけを返し、環境変数やヘッダーの値を renderer へ送らない。
- **原子的な書き込みの残骸とハードリンク** — `common/fs/atomicFile.ts` の `writeFileAtomic` は、書き込む先のディレクトリに残った一日より古い `.adk-tmp-*` を削除する（`.bak` と `.rename` は元のファイルの唯一の写しになり得るので残す）。ハードリンクのファイルは元の内容を `.bak` へ退避してからその場で書き込み、失敗したら元の内容へ戻す。戻せなければ `.bak` を残してログに記録する。distro 内の書き込みスクリプト（`wslFileScripts.ts` の `buildWriteScript`）も同じことを行う。
- **スキル一覧の補足情報** — スキルタブ（および Claude / Codex の公式スキルのインポートダイアログ）でも説明列の下に同じ方針・形式で補足表示する。対象は実行モデル・推論レベル・実行形態・確認なしで許可するツール・呼び出され方に限る。Claude が `model` / `effort` / `context` / `allowed-tools` / `disable-model-invocation`（既定 `false` は非表示）/ `user-invocable`（既定 `true` は非表示）、Grok が Grok Build のスキル解析（`xai-grok-tools` の `ParsedFrontmatter`）が読むキーのうち `model` / `effort` / `allowed-tools` / `disable-model-invocation` / `user-invocable`、Codex が `<skill>/agents/openai.yaml` の `policy.allow_implicit_invocation`（既定 `true` は非表示。一覧取得時に `policy.*` をメタへ加える）、OpenCode が `metadata` 内の `opencode/autoinvoke`（既定 `true` は非表示）と `disable-model-invocation`（既定 `false` は非表示）。Agy はスキル frontmatter に `name` / `description` 以外の公式キーが確認できないため対象外。`argument-hint` / `paths` / `disallowed-tools` / `agent` / `when_to_use` / `license` / `compatibility` などは一覧での重要度が低いため表示しない（ヘッダ参照で確認できる）。
- **frontmatter の読み取り範囲** — `main/utils/frontmatter.ts` は依存を増やさずテキストで YAML を読み、スカラーを YAML の書式どおりに復元する: プレーン（インデントした継続行は空白で連結）、ダブルクォート（`\"` `\n` `\uXXXX` などのエスケープを解釈）、シングルクォート（`''` を `'` に戻す）、改行をまたぐ引用符（YAML の折り返し規則で連結）、ブロックスカラー（`|` は改行保持、`>` は折り返しを空白に置換。チョンプ `-` / `+` とインデント指示子に対応）。フロー形式のリスト（`[a, b]`。引用符内のカンマは区切りとしない）とスカラー項目だけのブロックシーケンス（`- a` 行。キーと同じインデントの `- ` も可）はカンマ区切りの 1 行文字列にまとめる。値が空のキーに続くマップは 1 階層目の値を `親キー.子キー` として加える（2 階層目以降とマップを項目に持つシーケンスは対象外で、親キーの値は空文字列のまま）。行末コメント（空白に続く `#` 以降）は除去し、空白の前置が無い `#`（`provider/model#variant`）は値の一部として残す。`description: Use when: X` のように YAML としては不正でも各 CLI が受け付ける「値中の `:`」は値の一部として読む。実在する SKILL.md / エージェント定義（各 CLI の配置先と公式スキルリポジトリ）で `yaml` パッケージの解釈と一致することを確認済み。同じ規則で frontmatter 以外の YAML を読む `parseYamlScalars` も提供する。一覧の各列（説明を含む）は各 agent の定義形式（SKILL.md・エージェント md は YAML frontmatter、Codex のエージェントは TOML）のヘッダー値だけを表示し、本文から推測した値で補わない（description 未指定なら空欄）。説明列などのツールチップは改行を保持して全文を表示し、表示値の前後の空白・改行は除く。
- **Agent・Skill 一覧の参照列** — 各行に「ヘッダ」（frontmatter のみ）と「全体」（ファイル内容全体。agents=ファイル本体 / skills=SKILL.md。IPC `<agent>-asset:read-entry`）の 2 つの参照ボタンを 2 行で表示する。
- **設定の直接編集ダイアログ** — ダイアログを固定高（85vh）とし、スクロールはテキストエリア内の 1 本のみ（ネストスクロールなし）。全文は開くときに `readRaw` で読む（`read` はファイルの全文を返さない）。開いた時点の revision を保存時に渡し、ファイルが変わっていれば再読み込みか編集に戻るかを選ばせる（§3.9）。改行はファイルに揃え、ファイルの BOM を保つ。保存中の入力は、送った内容と違えば保存の完了後も未保存の編集として開いたままにし、次の保存は保存の結果の `revision` を使う。未保存の編集があるときの Escape とキャンセルは破棄してよいかを確認する（`TextFileEditorDialog` も同じ。読み取り専用と、編集していないときは確認しない）。ダイアログが閉じ終わったら（`onExited`。保存で閉じるときは、再読み込みでダイアログが取り除かれても残らないよう閉じる時点で）、保持していた本文を state から捨て、もう一度描画して React が 1 つ前の描画として持つ控えからも消し（`useRenderAgainAfterDiscard`）、次に開くときは読み直す（`TextFileEditorDialog` も同じ）。ダイアログに重ねて開くダイアログの前には `StackedDialogFocus` を置き、下のダイアログのフォーカスを外してから aria-hidden の範囲に入れる。
- **プラグイン管理（共通実装）** — 画面本体は agent 非依存の `renderer/components/plugins/PluginManagerView` で、各 agent の画面は API と文言キーを渡す薄いラッパー。機能差（直接インストール、npm package、カタログ、マーケットプレイス管理、リモート marketplace URL、直接インストール画面の説明文 `sourceHelpKey`）は `PLUGIN_CAPABILITIES` に宣言する（`sourceHelpKey` は Agy / OpenCode が指定し、省略時は @ref / #subdir 書式の共通説明）。カタログ/マーケットプレイス非対応のAgy/OpenCodeでは該当タブや操作を表示せず、直接ソース導入だけを表示する。`PluginEntry` の `uninstallable` / `toggleable` が `false` の行は、アンインストールボタン・有効/無効トグルを無効化し、理由をツールチップで示す（Claude のマーケットプレイス以外の由来はアンインストール不可、Codex のリモートカタログ由来は切り替え不可）。追加ダイアログのカタログ一覧は 200 件ずつ描画し、「さらに N 件表示」で追加表示する（絞り込み条件を変えると先頭に戻る）。マーケットプレイスの絞り込み候補は、インストール元として選択可能なマーケットプレイスに、カタログ項目の提供元（`marketplace list` に現れない組み込みカタログなど）を加えたもの。画面の「再取得」は `<agent>-plugin:get-environments` に `refresh=true` を渡し、`AgentCliRunner` と `WslDetector` の検出結果を破棄してから環境を列挙し直す（いずれかの環境で操作の実行中は押せない）。アンインストールの確認ダイアログには、一緒に削除される同じリポジトリのプラグイン（`PluginEntry.sameRepoPlugins`。Grok のみ）を列挙する。CLI の失敗理由のうち機械コード（`needs-reconfirm`・`invalid-argument-percent` など）は `pluginMessage.ts` が文言に置き換えて表示し、長い CLI の出力は先頭 1,000 文字と末尾 3,000 文字を残して中略する。CLI変更操作は `AgentCliRunner` を使う。OpenCode はパッケージの導入に `opencode plugin add` を使い、そのほかは公式設定ファイル/ディレクトリを差分編集する。詳細は §3.7 参照。
- **共通画面の再利用** — Agy / OpenCode の MCP / Agent・Skill / 設定 / クリーンアップ画面は agent 非依存の共通ビュー（`renderer/components/agent/`）で実装し、既存 agent（Claude / Codex / Grok）の画面と同一のレイアウト・操作性・文言スタイルを保つ。`App.tsx` は機能ルートの要素にルートごとの key を付け、同じ部品を使う画面の間を直接移動しても状態を引き継がない。共通ビューと `PluginManagerView` は `useAgentEnvironments` で環境を読み、対象のエージェントか API が変わると前の一覧を描画せずに読み直す（最後に始めた読み込みだけを使う）。環境セクションの key にもエージェントを含める。設定画面の directEdit 項目は、`linkTab` か `linkRoute` があれば値欄に編集先へのリンクを表示し、無ければ「ファイルを直接編集」のテキストを表示する（§3.8）。
- **設定の読み取りの範囲** — 5 つの設定マネージャーの `read` は登録項目の値だけを返し、ファイルの全文を返さない。全文は直接編集ダイアログを開くときの `readRaw`（IPC `<agent>-settings:read-raw`、Codex / Grok は `<agent>-config:read-raw`）だけが返すので、スコープ編集で伏せている本文は設定の表の読み取りでは renderer に届かない。
- **失敗の詳細** — 解釈の失敗と編集の失敗は、例外のメッセージではなくコードと位置だけを渡す。`SettingsParseError` は `code`（`json-syntax`、`json-root`、`toml-syntax`）と `line`、`column`、`position` を持つ。`ConfigFileError` の詳細は `formatConfigDetail` の形（`code=toml-syntax;line=2;column=11`）で、renderer の `configDetailText` が `common.configDetail.*` の文言にする。OS のエラーコードと項目の名前はそのまま表示する。プロファイル設定の `detail` のパスのコード（`too-deep`、`unsafe-segment`、`reserved-name`、`case-conflict` など）は `common.profile.warning.*` の文言にする。
- **i18n** — 日本語/英語。共通文言は `locales/<lang>/app.ts`、agent 固有文言は `locales/<lang>/<agent>.ts` に分離し、`<agent>.*` の名前空間で参照する。プロファイル設定のタブの見出しと文言は `<agent>.profile.*`、編集部品の文言は `common.profile.*`。日本語は英単語・パスの前後に半角スペースを置き、本文・タブ・設定ラベルはカタカナ表記（エージェント/スキル/プラグイン）で統一する。

### 3.7 プラグイン管理の CLI 連携仕様

各 agent CLI のプラグイン仕様（2026-10-15 に Claude Code 2.1.296 / Codex 0.162.1 / Grok 1.0.50 / Agy CLI 1.3.3 / OpenCode 2.0.29 の実機・公式資料で検証）。CLI はすべて `AgentCliRunner` 経由で、ホームディレクトリを作業ディレクトリとして実行する（§2.3）。

**実行するコマンド（マネージャごとの対応表）:**

| 操作                   | Claude                                                                                              | Codex                                                                                                             | Grok                                                     |
| ---------------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| インストール済み一覧   | `claude plugin list --json`                                                                         | `codex plugin list --json`                                                                                        | `grok plugin list --json`                                |
| カタログ               | `claude plugin list --available --json`                                                             | `codex plugin list --available --json`                                                                            | `grok plugin list --available --json`                    |
| マーケットプレイス一覧 | `claude plugin marketplace list --json`                                                             | `codex plugin marketplace list --json`                                                                            | `grok plugin marketplace list --json`                    |
| インストール           | `claude plugin install <p>@<market>`                                                                | `codex plugin add <p>@<market> --json`                                                                            | `grok plugin install <p>@<qualifier> --trust`            |
| 個別リポジトリから     | 非対応（2 段階方式）                                                                                | 非対応（2 段階方式）                                                                                              | `grok plugin install <src> --trust`（@ref / #subdir 可） |
| アンインストール       | `claude plugin uninstall <id>`                                                                      | `codex plugin remove <id> --json`                                                                                 | `grok plugin uninstall <name> [--confirm]`（下記）       |
| 有効/無効切り替え      | `claude plugin enable\|disable <id> --scope user`（マーケットプレイス以外の由来はスコープ指定なし） | サブコマンド無し → config.toml の `[plugins."<id>"] enabled` を直接編集（対象行のみ。リモートカタログ由来は不可） | `grok plugin enable\|disable <name>`                     |
| マーケットプレイス追加 | `claude plugin marketplace add <src>`                                                               | `codex plugin marketplace add <src> --json`                                                                       | `grok plugin marketplace add <src>`                      |
| マーケットプレイス削除 | `claude plugin marketplace remove <name>`                                                           | `codex plugin marketplace remove <name> --json`                                                                   | `grok plugin marketplace remove <name>`                  |

**Claude 固有の扱い:**

1. `claude plugin list --json` はインストール（スコープ）ごとに 1 要素で、他プロジェクトの project / local スコープも含むため、`CLAUDE_LISTED_PLUGIN_SCOPES`（user / synced）のスコープだけを残し、同一 ID の重複も除く。ID（`<name>@<origin>`）は最後の `@` で名前と由来に分ける。
2. マーケットプレイス以外の由来（`CLAUDE_NON_MARKETPLACE_PLUGIN_ORIGINS` = inline / skills-dir / synced / builtin）はインストール記録が無く `claude plugin uninstall` の対象にならないため、アンインストールは CLI を実行せずに拒否し（`uninstallable: false`）、有効/無効の切り替えだけを許可する。
3. enable / disable は、マーケットプレイス由来のプラグインに `--scope user` を付ける（省略すると実行時の作業ディレクトリの project / local 設定から書き込み先が自動判定されるため）。マーケットプレイス以外の由来は CLI が user 設定の `enabledPlugins` へ書き込むため、スコープを付けない。
4. 変更操作は、操作対象（プラグイン ID・ソース・マーケットプレイス名）が空、または `-` で始まる場合、CLI のオプションとして解釈されるのを防ぐため実行しない。
5. マーケットプレイス一覧のソース表示は、github / git で ref を固定している場合 `#<ref>` を付ける（`marketplace add` と同じ表記）。
6. カタログには予約済みの組み込みマーケットプレイス `anthropic-plugin-directory` のプラグインも含まれる。

**Codex 固有の扱い:**

1. 有効/無効は config.toml の `plugins."<id>".enabled` の値だけを直接編集する（`CodexPluginManager.applyEnabled`。他のセクション・コメント・整形は保持する）。既存の `enabled` は書き方（`[plugins."<id>"]` 見出し・ドット記法・インラインテーブル）を問わず値だけを置き換え、無ければ見出しの直後・インラインテーブルの先頭・ドット記法の行の直後に加えるか、末尾に `[plugins."<id>"]` ごと追記する（見出しと代入の位置は `main/utils/tomlStatements.ts` の `scanTomlStatements` で求める）。編集前の TOML が読めない場合、`plugins` / `plugins."<id>"` がテーブルでない場合、編集結果を読み直した内容が「`enabled` だけを変えた内容」と一致しない場合は、書き込まずに失敗を返す。Codex はこの設定をローカルマーケットプレイスのプラグインにだけ適用するため、リモートカタログ由来（`plugin list --json` の `source.source = remote`）は `toggleable: false` とし、書き込まずに失敗を返す。
2. インストール済みプラグインが参照しているのに `marketplace list` に無いマーケットプレイス（リモートカタログ `openai-curated-remote` など）は、CLI から削除できないため削除不可（origin='builtin'）として一覧へ補う。
3. カタログは pluginId で重複を除き（インストール済みを優先）、インストール不可（`installPolicy = NOT_AVAILABLE`）の未インストールエントリは返さない。
4. `plugin list --available --json` には description が含まれないため、best-effort で補完する。ローカルのプラグインは `source.path`（プラグイン実体）のマニフェストを読む。名前・説明などの識別情報はルートの `plugin.json` を正とし、無ければ `.codex-plugin/plugin.json` を使う。OpenAI 固有の `interface`（shortDescription / websiteURL）はルートの `extensions["com.openai"]` があればそれを、無ければ `.codex-plugin/plugin.json` のものを使う（`HomeFs.readAbsoluteStrict` で読むので、WSL は distro の中で読む。読めなければ空のまま）。リモートのプラグインは `source.id` をキーに `~/.codex/cache/remote_plugin_catalog/*.json`（`schema_version` 1 のみ対応）から読み、読めない場合（WSL のコマンドモードを含む）は補完しない。

**Grok 固有の扱い:**

1. マーケットプレイス指定子は表示名ではなく qualifier。Grok の addressable_qualifier と同じ規則で、GitHub の Git ソースは `owner/repo`（小文字）、それ以外の Git ソースは `git/<slug>`、ローカルソースは `local/<slug>`（slug は ASCII 英字を小文字化し、空白の連続をハイフン 1 個にしたもの）。`GrokPluginManager.catalog()` が marketplace list の kind / URL から組み立てる。
2. `grok plugin list --json` には無効状態が出ないため、有効状態は config.toml の `[plugins] enabled / disabled` から Grok と同じ規則で判定する（enabled に含まれ、かつ disabled に含まれないものだけが有効。どちらにも無いインストール済みプラグインは無効）。要素はプラグイン名、または user スコープの ID `user/<hash>/<name>`。config.toml を読めない場合は、インストール時に自動で有効化される CLI の既定動作に合わせて有効とみなす。
3. `uninstall --confirm` は同じリポジトリ（`repo_key`）からインストールした他のプラグインも削除する（`--confirm` が無いと、他のプラグインがあれば CLI は削除しない）。一覧では同じ `repo_key` の他のプラグイン名を `sameRepoPlugins` に入れ、確認ダイアログで一緒に削除されるものとして示す。アンインストールでは、確認したプラグイン名（`confirmedNames`）を受け取り、実行の直前に `plugin list --json` で同じリポジトリのプラグインを調べ直す。他のプラグインがすべて確認済みなら `--confirm` を付けて実行し、他のプラグインが無ければ `--confirm` を付けない。確認していないプラグインが増えていた場合は実行せず `needs-reconfirm` を返し、画面は一覧を取り直して確認し直せるようにする。
4. `marketplace remove` はそのソースからインストールしたプラグインもアンインストールする。Grok はアンインストールとマーケットプレイス削除のどちらでも `[plugins] enabled / disabled` から名前を取り除かないため、本アプリが実行前に対象のプラグイン名を集め、成功後に両方のリストから取り除く（代入の書き方を問わず対象の配列の値だけを 1 行に書き換え、再パース結果が期待と一致しなければ書き込まない）。
5. マーケットプレイスの削除は CLI だけで行い、config.toml を直接編集しない（上記の名前の除去を除く）。Claude 由来の外部マーケットプレイス（origin='external'）は、CLI の remove が `~/.claude` 側の設定ファイルも書き換えるため、本アプリからは削除しない（削除ボタンを無効化）。

**ソース種別と互換性:**

- Agy CLI: `agy plugin install <target>` / `uninstall <name>` / `enable|disable <name>` を使う。導入元は `<name>@antigravity-plugins-official`（公式マーケットプレイス）・プラグイン名・GitHub リポジトリ URL・ローカルフォルダ。`~/.gemini/config/plugins` はGemini CLI共通だがAntigravity CLIの正式対象である。`agy plugin list` は import した Plugin しか列挙しないため、一覧はディレクトリ走査で構築する。CLI の操作対象はプラグイン名（`plugin.json` の `name`。無ければディレクトリ名）で、CLI に渡せない名前の Plugin は切り替え・削除できないものとして表示する。公式マーケットプレイスは存在するが、カタログ・マーケットプレイスを扱う CLI コマンドが無いため、カタログとマーケットプレイスUIは提供しない。

- OpenCode（`OpenCodePluginManager`）: リポジトリ形式のカタログ/マーケットプレイスUIは提供しない。OpenCode 2 と判定できない環境ではプラグイン画面を操作不可として表示する。
    - 設定ファイルの要素: グローバル設定ファイル（§3.5。両方のファイルを読み、指定のあるファイルを `definedIn` で返す）の `plugins` 配列の要素は、指定子の文字列か `{ package, options }` である。指定子は npm パッケージ指定（`@scope/name@version` など、提供元は npm と表示）、Git 指定（`github:owner/repo#ref`・`git+https://…`・`owner/repo` など、提供元は git）、ファイルパス（`file://`・`./`・絶対パス、提供元は file）のいずれか。有効化の指示（`-<ID>`・`*`・`<接頭辞>.*`・組み込み ID `opencode.*`）は一覧に出さず、位置を保って残す。同じ指定子が重複していても 1 行にまとめる。
    - パッケージの導入: `opencode plugin add <指定子>`（タイムアウト 5 分）で行い、取得と設定への追加は OpenCode が行う。無効化した同じ指定子が退避されていた場合は、導入後に退避先から外す。
    - 要素の単位の編集: `plugins` 配列は `jsoncEdit` の `readJsoncArray`、`removeJsoncArrayElements`、`insertJsoncArrayElements` で編集し、他の要素の原文とコメントを保つ。要素は原文のまま移すので 2^53 を超える数値も丸めない。`plugins` が配列以外の値のときと、編集の結果の検証に失敗したときは何も書かない。
    - 無効化・有効化と並び順: 無効化は指定のあるすべてのファイルから要素を除いて `opencode-disabled-plugins.json` の `plugins` へ移し、ファイルごとの記録を `positions.<指定子>.origins` に入れる（`file` はファイル名、`items` は退避した要素、`order` は無効化した時点の `plugins` 配列の並びで、無効化中の他の要素も記録した位置に戻したもの）。元のファイルの記録が無い要素は `resolveOpenCodeConfigRel` のファイルへ戻す。OpenCode は先頭から評価して後ろの指定が勝つため、有効化では記録した並びに沿って元の位置へ戻す（手前にあった要素のうち残っている最も近いものの直後。手前の要素が残っていなければ、先頭にあった要素は先頭へ、それ以外は後ろにあった要素のうち残っている最も近いものの直前へ）。位置の記録が無い・位置を決められない場合は末尾へ置く。他の要素（有効化の指示を含む）の順序は変えない。位置の記録は退避中の要素の分だけを残し、退避ファイルが空になったらファイルごと削除する。
    - 退避ファイルが JSONC として読めない場合は、一覧では無効化中の分を空として扱って警告（`opencode.plugins.disabledFileInvalid`）を添え、設定ファイルの要素の有効化・無効化・削除とパッケージの導入は行わない（`invalid-disabled-file`）。
    - ターミナル UI の設定 `~/.config/opencode/cli.json` の `plugins` 配列（`opencode plugin add` が TUI 専用のパッケージを追加する先）は、読み取り専用で一覧に出し（`uninstallable` / `toggleable` を `false` にして注記）、有効化・無効化・削除はしない（`read-only`）。
    - ローカル Plugin: `~/.config/opencode/plugins` 直下の `.ts` / `.js` とプラグインフォルダー（`package.json`、または `index` / `server` / `tui` の `.ts` / `.js` を含むもの）。絶対パスの指定により `plugins/` へコピーして導入し、同名の既存分は置き換え、無効化中の同名分は削除する。導入元自体がリンクの場合は導入しない（`invalid-plugin-source`）。導入元と導入先は実体（デバイスとファイル ID）で比べ、導入先そのものなら `already-exists`、導入元が `plugins` かその上位のフォルダー、または導入元が既存の導入先の内側にあるなら `source-overlaps` として何もしない。フォルダーの中のリンクは辿らず、コピーもしない。コピーは `plugins` の隣の一時フォルダー（`.plugin-install-XXXXXX`）に作ってから置き換え、途中で失敗したときは旧版を残す（使用中で既存の導入先を移動できなければ `move-in-use`）。WSL は本文を distro のスクリプトで送って同じ手順で置き換え（`installFiles`）、distro の中のパスを指定すれば distro の中で読み取る。フォルダーの有効と無効の切り替えは `HomeFs.moveEntry` で移動する。
    - ローカル Plugin の無効化・再有効化は `plugins/` と `plugins-disabled/` の間の移動で行う（使用中で移動できなければ `move-in-use`）。アンインストールは設定ファイルの要素の除去（退避先の分を含む）、またはローカルのファイル/フォルダーの削除で、パッケージの実体は OpenCode が管理する。

- マーケットプレイスソース: Claude = owner/repo / Git URL（`#ref` 可）/ ローカルパス / リモート marketplace.json URL。Codex = ローカルパス / `owner/repo[@ref]` / HTTPS・SSH Git URL（URL 直接指定は不可）。Grok = Git URL / owner/repo / ローカルディレクトリ。
- **3 CLI とも Claude 形式のマニフェスト（`.claude-plugin/marketplace.json` + `plugin.json`）を読める**（実機検証済み）。このため「個別リポジトリからの追加」の 2 段階方式（マーケットプレイスとして追加 → 含まれるプラグインを選択）は同一リポジトリで 3 CLI 共通に運用できる。
- 組み込みマーケットプレイス（削除不可扱い）: Claude = `claude-plugins-official`、Codex = `openai-bundled` / `openai-primary-runtime` / `openai-curated` / `openai-curated-remote`、Grok = `xAI Official`。定義は各 `constants.ts` の `*_BUILTIN_MARKETPLACES`。

### 3.8 プロファイル設定タブ

対象はユーザープロファイル配下の各エージェント専用ディレクトリだけで、プロジェクトやワークスペースのファイルは扱わない。

**構成:**

| 層 | ファイル | 役割 |
| --- | --- | --- |
| 仕様 | `shared/agents/profile/types.ts`、`shared/agents/profile/channels.ts`、`shared/agents/profile/pathLabels.ts`、`shared/agents/<agent>/profileTabs.ts` | 共通側は section の種類と IPC の形だけを定義する。タブの一覧、ID、構成は各エージェントの `AgentProfileSpec`（`docs`、`settingsDoc`、`settingsTabs`、`assetTabs`）が持ち、renderer へ IPC で渡す純データにする。 |

**画面の動作:**

- タブの定義: CLI に機能がないタブは定義しない。定義したタブはファイルが 0 件でも表示する。フォルダーが無ければ空の一覧を出し、新規作成やアップロードの時点でフォルダーを作る。未作成の指示ファイルは未作成の行として並べ、未設定のキーには `emptyTemplate` の雛形を出す。
- タブの状態: `ProfileTabsShell` は環境セクションごとにタブを持ち、ルートを分けない。一度開いたタブは `display:none` でマウントしたままにするので、未保存の編集はタブの切り替えで失われない。選択中のタブは `useProfileTabSelection` が環境ごとに保持する。タブの定義を読めなければ設定タブだけを表示する。
- 再読込: `useProfileVersions` が文書と一覧ごとの保存回数を持ち、同じファイルを読む section を読み直す。編集中の section は読み直さず、編集が終わった時点で読み直す。更新ボタンは `reloadNonce` を変える。設定タブは `useSettingsLoadEffect` の `overlay` で、読み直した値に未保存の差分を重ねる。
- リンク行: `SettingsFieldSpec` の `linkTab`（同じ画面のタブの ID）か `linkRoute`（別の画面のルート）を持つ項目は、型が `directEdit` のままで、値欄に編集先へのリンクを表示する（`settingsTabContext.ts`、`SettingsValueEditor`）。文言は `common.profile.linkTo` と `<agent>.profile.tab.<linkTab>`、または `<agent>.profile.link.<key>`。機能のスイッチは編集可能型のまま残す。
- コマンドタブ: `assetTabs` の `commands` を `AssetManagerSection`（Claude / Grok）と `AssetManagerView`（OpenCode）が表示する（`ProfileAssetTab`）。`commands` は `AssetKind` に含めず、`FileCollectionManager` で扱う。OpenCode の `commands` の行は `linkRoute` の `/opencode/agent-skill?tab=commands` でこのタブを開く。
- タブの本文: タブの直下に本文を置く。固定の説明、固定の注記、対象のパスの行は持たない。`titleKey`（見出し）は見分ける必要のある section が 2 つ以上あるタブだけが持ち、タブの名前を繰り返さない。`scopedEditor` の編集ダイアログの題名は `editorTitleKey` が持つ。
- 注記: 今の状態についてのものだけを 1 文で出す（読み取りの失敗、`conditionalNotices`、別の書き方の併記、読めない `disabled-hooks`、一覧を読み切れなかったフォルダ）。保存時の検証の警告は確認のダイアログに出す。
- パスの表示: パスを出すのは編集ダイアログの説明の 1 か所だけ。行の名前は `shortestDistinctPaths`（`shared/agents/profile/pathLabels.ts`）で、ほかの行と見分けられる最小の部分にする（指示ファイルの行、hook の定義元の列）。ファイル一覧は一覧のフォルダからの相対の名前を出す。
- 警告の確認: 警告を出す API は `confirmedWarnings` を受け取る。未確認なら `needs-confirmation` と警告のコードを返して何も変えず、確認後の再送で保存する。

**section の種類:**

**タブごとの補足:**

- 共通: 再帰で読む一覧の表示の深さの上限は 16、読み込まれない深さのファイルを出す深さは 4。
- Claude: `exactExtensionCase` のある一覧は `.MD` などを「読み込まれない」と表示する。出力スタイルの表示名は frontmatter の `name` を優先し、組み込み名と同じなら注記する。ワークフローの表示名は先頭の `export const meta` の `name` で、`.mjs`、`.cjs`、`.ts` は読み込まれない行にする。コマンドの表示名は `/a:b` で、`skill.md` のあるフォルダーの他のファイルは読み込まれない行にする。`sandbox.ripgrep` は `sandbox` の他のキーを変えない。
- Codex: `.rules` のシンボリックリンクは読み込まれない行にする。`default.rules` の削除は警告を確認してから行う。指示ファイルの削除で有効なファイルが移るときは `delete-effective-moves` で確認する。
- Agy: 権限の形式の合わない要素は警告にとどめる。指示ファイルの削除の確認で App / IDE との共有を示す（`sharedWarningKey`、`delete-shared-file`）。sidecars は `<id>/sidecar.json` だけを読み込まれる行にする。
- Grok: `permission.rules` と `allow` / `ask` / `deny` は `otherForm` で管理する。片方の書き方だけがある文書に別の書き方を足す保存は `other-form-present` で拒否し、両方ある文書は確認のうえ保存する。`grok_com_config.auth_provider_command` があれば `[auth]` の編集が効かない旨を注記する。ワークフローのサブフォルダーの `.js` は「読み込みを保証しない」と表示する。
- OpenCode: 文書は `resolveOpenCodeSettingsRel` が選ぶ。`opencode.json` と `opencode.jsonc` が両方あれば `opencode.profile.bothConfigFiles` で、編集していない方の値が有効なまま残ることを注記する。旧キー `permission` が残っていれば注記する。旧形式の `command/` は同じ名前の `commands/` に隠れる行に `shadowed-by` の警告を付け、設定ファイルの `commands` のキーがファイルに隠れていれば注記する。frontmatter が閉じていないファイルは読み込まれない行にする。

**固定ファイル:**

- 実ファイルの解決: 正式名と大文字小文字だけ違うファイル（`Agents.md` など）は、正式名の行に読み込む（`resolveFixedFile`）。保存後に実ファイルの名前が正式名と違えば、一時名を経由して改名し、一覧で確かめる（`ensureCanonicalName`。揃わなければ `canonical-rename-failed` の警告）。大文字小文字を区別するファイルシステムで改名すると読み込み順が変わるので `rename-changes-load-order` で確認する。
- 両方ある場合: 大文字小文字だけ違う別ファイルは `variants` で表示し、消さない。`mergeFixedFileVariants` は確認（`merge-changes-load-order`）のうえ、別ファイルの内容を先に置いて正式名のファイルへ統合し、別ファイルを消す。統合する内容が無ければ（すべて空白だけなら）正式名のファイルへ書かず、別ファイルだけを消す。改名で読み込み順が変わる保存（`rename-changes-load-order`）は、本文が同じでも確認されるまで何も変えない。`AGENT.md` は別の名前なので別の行のまま。
- 空の保存: 空のファイルを作る保存は main が `empty-content` で拒否し、画面は確認のうえ `deleteFixedFile` を呼ぶ。シンボリックリンクはリンク自体だけを消す（`delete-link-only`）。`sharedWarningKey` のある section は `delete-shared-file`、`firstNonEmpty` の section で有効なファイルが移るときは `delete-effective-moves` の確認を求める。

**ファイル一覧:**

- パスの検証: `validateRelPath` で絶対パス、ドライブ指定、安全でないセグメント、拡張子、深さを検証し、作成時は予約名も拒否する。`findLinkBelowRoot` でルートより下の中間のリンクを拒否する。ルート自身のリンクは許容する。
- 読み取り専用: シンボリックリンク、リンク切れ、UTF-8 として読めないファイルは読み取り専用の行にする。
- 削除: 空になった親フォルダーをルートの手前まで片付ける。
- ZIP: アップロードは `inspectUpload` で確かめたファイルだけを、確かめた環境と一覧で受け付ける。全エントリを新しいパスとして検証し（`validateArchiveEntries`）、深さの上限を超えるものは `nested-not-allowed`、大文字小文字だけ違うパスの組は `invalid-archive` で拒否する。CLI がルートを再帰で読む一覧（`maxDepth` が 1 以上）は、作業フォルダーをルートの外に作る。

**保存前の検証（`profileValidators.ts`）:** 保存を拒否するのは文書の形式として読めない内容（`json-strict`、`jsonc`、`codex-hooks-json`、`grok-lsp-json`、フックの 1 件の JSON、TOML の断片）と、Codex が起動できなくなると確認した `[hooks]` の形（`validateCodexHooksFragment`）だけにする。それ以外は警告にとどめ、確認のうえ保存できる。結果はコードだけを返し、入力の本文を含めない。

**フックの表の編集（`ProfileManager`、`hookEntryEdit.ts`）:**

- 行と位置: 行は `locator`（`source`、`name`、`event`、`group`、`handler`）と読み取り元のファイルの `revision` を持つ。`source` は main が決める `doc:<文書 ID>` か `file:<一覧のファイル名>` で、main は読み取り元の今の一覧から探す。`handler` が null の行はイベントの配列に直接書かれたハンドラ（Agy）。`invalid` のグループやイベントの行、`custom` の行、リンクのファイルの行（`linked`）、`hooks` が空のグループの行は `locator` を持たない。
- 編集のテキスト: `{ "matcher": ..., "hooks": [ { ハンドラ } ] }` の JSON。グループの `hooks` 以外のキーも含め、無いキーは出さない。解釈できなければ `invalid-input` と形の違いのコード（`hook-entry-not-object`、`hook-entry-hooks-missing`、`hook-entry-hooks-empty`、`hook-entry-handler-not-object`、`hook-entry-matcher-not-string`、`hook-entry-null-value`、`json-invalid`）を返し、`TextFileEditorDialog` がテキスト欄の上に出す。
- 置き換え: `hooks` 以外のキーが同じなら、そのハンドラの位置へ `hooks` の要素を入れる（1 件以上）。違えば、ハンドラをグループから取り出し、同じ位置（`group`）へ新しいグループを入れる。元のグループに残りがあれば、元のグループは 1 つ後ろへ移る。元のグループが空になるなら、新しいグループで置き換える。内容が同じなら書き込まない。
- 追加: イベントの配列の末尾へ入れ、無いキーは作る。Agy で matcher が効かないイベントは、ハンドラを配列へ直接並べる。Grok は同じイベントを別の書き方で表すキー（`pre_tool_use` など）が文書にあれば、そのキーへ入れる（`isSameGrokEvent`）。Agy の hook の名前は追加のダイアログで指定する。
- 削除: `deleteHookEntry` は確認の前に呼ぶと何も変えず `needs-confirmation` と警告を返す。画面はコマンドを示して確認する。グループが空になればグループを、配列が空になればイベントのキーを、`hooks` が空になれば `hooks` のキーを取り除く。Agy は `enabled` だけが残った hook の名前も取り除く。`hooks.state` が残る `[hooks]` は残す。
- 競合: `revision` はファイル全体のもので、開いた後にファイルが変わっていれば `conflict` を返して書き込まない。
- JSON の文書: `jsoncEdit.ts` の `replaceJsoncValueAt`、`removeJsoncElementAt`、`insertJsoncElementAt` で対象の値の原文だけを置き換える。結果を解釈して期待する値と比べる（`verify-failed`）。
- TOML の文書: `tomlSubtree.ts` の `editTomlArrayItems` で配列テーブルの要素だけを編集し、`verifyTomlEdit` で検証する。ハンドラの本文はキーごとに値の原文だけを置き換えるので、行末のコメントと並びの順は残る。`hooks = [...]` の形はインライン配列の要素だけを置き換える。イベントが `Event = [...]` の値で書かれていれば、その値を書き直す。`hooks` がインラインテーブルなら `inline-parent` で拒否する。文書全体のコメントを編集の前後で比べ、失われるものがあれば `hook-comments-lost:<件数>` で確認する。
- BOM と改行: 改行はファイルに揃え、BOM は `bomAfterSave` に従う（`hooks.json` と `hooks` フォルダーの `*.json` は BOM なしで保存する）。すべての読み書きは `HomeFs` を通すので、WSL でも同じに動く。
- 検証: `entryValidator` は編集する 1 件、`fileValidator` は編集後のファイル全体を検証する。`config.toml` の `[hooks]` は `codex-hooks` で起動エラーになる形を拒否する。`hooks.json` の同じ形はファイルごと読み飛ばされるので、`codex-hook-entry-json` で警告にする。Grok は `grok-hooks` で警告する。
- 再読込: `hookOverview` の保存は読み取り元の文書と一覧の版を進める。設定タブの `hooks` の行は `linkTab` でこのタブを開く。

**Grok のフック名と `disabled-hooks`（`hookOverview.ts`）:**

- 名前: `.grok/hooks/<stem>.json` は `global/<stem>:<event>[<グループ番号>].hooks[<ハンドラ番号>]`、`config.toml` は `user:<event>[<グループ番号>].hooks[<ハンドラ番号>]`。`<event>` は snake_case で、番号はイベント内の記述順で 0 始まり。既知の書き方（snake_case、PascalCase、camelCase、別名の `subagent_end`）はイベントの表示名に揃える。`<stem>` はファイル名から最後の拡張子を除いたもの。
- 名前を付けない行: 同じ読み取り元に未知の書き方のイベントがある場合（番号を断定できない）、同じイベントを別の書き方で併記している場合（連結の順が定まらない）、JSON でファイル全体、TOML でそのイベントが読み込まれなくなる形の崩れがある場合、読み込まれないハンドラ（行を `invalid` にする）。
- 無効化の行: `.grok/disabled-hooks` は 1 行 1 名で、空行と `#` で始まる行は名前ではない。保存時にコメントと未知の行をそのまま残し、改行はファイルに揃える。読めないファイルは `unreadable` として状態を断定せず、切り替えもしない。
- 状態: `enabled`、`disabled`、`maskedByOtherCopy`（別のコピーの無効化で止まっている。`maskedBy` に相手の名前）。コピーは同じイベント、matcher、ハンドラ（http は URL、それ以外は解決したコマンドと `args`、`env`）の組で判定し、`config.toml` の方が `hooks/*.json` より強く、同じ強さでは先に読み込まれる方が相手を止める。
- 切り替え（`planHookToggle`）: 有効化は自分の行と自分を止めている行を消し、相手の名前を `hook-enable-removes` で確認する。無効化は自分の行を足し、一緒に止まる相手の名前を `hook-disable-also-stops` で確認する。
- 編集時の追従: 名前は位置の番号を含むので、表の編集と削除で位置が変わる hook の名前を、同じ操作で無効化の行へ反映する（`renameDisabledHookLines`）。削除した hook の行は消し、コメントと未知の行は残す。`disabled-hooks` を読めなければ、追加以外の編集はしない。反映に失敗すれば `hook-disabled-list-not-updated` を返す。
- フックファイルの一覧: `.grok/hooks/*.json` は同じタブの `hooks-files`（`fileCollection`）で一覧、作成、削除、ZIP の入出力を行う。作成とアップロードの内容は `grok-hooks` で検証する。
- `hooks-paths`: `.grok/hooks-paths` は 1 行 1 絶対パスの登録簿で、指す先の hook を `custom` の行として読み取り表示する（編集と削除の操作を出さない）。`.grok` の外は読まず、読めない行として示す。一覧の読み取り元と重なるパスは飛ばし、ディレクトリは直下の `.json` を読む。

**形の崩れたフックファイル:** イベントの値が配列でないなど、1 件を指せない行は `repairSource` を持ち、`readHookSourceFile` と `saveHookSourceFile` でファイル全体を編集する。対象は設定ファイル本体（直接編集で直せる）以外の JSON の読み取り元で、JSON として読めない内容は保存しない。`savedNoteKey` を持つ section（Codex）は、保存の通知にその文を添える。

**秘密情報:** `sensitive` の section（`model_providers`、`auth_provider`）は、展開か編集の操作があるまで本文と revision を返さない（`withheld`）。

### 3.9 ファイル操作の基盤

**厳密な読み取りと原子的な書き込み（`common/fs/atomicFile.ts`、`common/wsl/HomeFs.ts`）:**

- `readTextStrict` は `ok`、`missing`（途中がディレクトリではない場合を含む）、`dangling-link`、`error` を区別して返す。`ok` は BOM を除いたテキスト、`hadBom`、`eol`、`mixedEol`、`revision`、`utf8Clean`、`isLink`、`linkTarget`、`identity` を持つ。読み取り → 変更 → 書き込みの経路はすべてこれを使い、読み取りエラーのまま書き込みへ進まない。UTF-8 として往復できない内容は編集を拒否する（`not-utf8`）。`readTextStrictMany` は WSL で 1 回のスクリプトの実行でまとめて読む。`readText` は欠損が無害な読み取り専用の用途に限る。
- `writeTextAtomic` は同じディレクトリの一時ファイル（`.adk-tmp-*`）に書いて同期し、権限を引き継いで rename する。シンボリックリンクは実体へ書いてリンクを残し、リンク切れは `dangling-link` で止める。ハードリンクはその場で書く。書き込み権限のない既存ファイルは置き換えない。
- 他の操作: `deleteStrict`（ファイルかリンクを 1 つ消す。`expectedRevision` と比較する）、`renameViaTemp`（一時名を経由した改名）、`listEntries`、`listTree`（作業用のエントリを含めない）、`findLinkBelowRoot`、`removeEmptyParents`、`realPathKey`、`resolveFollowedPath`、`statFile`。
- 改行: 統一は renderer から届いた編集テキストだけに、検証の前に行う（`normalizeEditedText`）。ファイル全体の保存はファイルの多い方の改行へ揃え、混在していたファイルは `mixed-eol-normalized` を返す。

**revision と競合:**

- revision は生のバイト列の sha256（16 進）。未作成は `missing`、リンク切れは `dangling-link`、リンク先が通常のファイルでないものは `link-to-non-file`。
- ファイル全体の保存（`saveFileText`、`saveWholeDoc`、固定ファイル、ファイル一覧）は、開いた時点の revision と違えば `conflict` と最新の内容を返して書かない。
- スコープ編集は断片の sha256 で比較するので、スコープ外の変更は競合にならない。`commandFields` と `orderedLists` はキーごとに比較する。`applyDocEdit` は読み取りの後に書き込みの前でファイルが変わっていたら 1 回だけ読み直す。
- 設定の直接編集（`saveDirectEdit`、`DirectEditDialog` の `useDirectEdit`）は開いた時点の revision を `baseRevision` で渡す。`TextFileEditorDialog` と直接編集は再読み込みか編集に戻るかを選ばせ、上書きの手段を持たない。
- 設定の表の保存（5 つの設定マネージャーの `write(env, values, base)`）は、変更した項目ごとに読み込んだ時点の値を `base` で渡す。保存時に読み直した現在の値（画面に見せる値と同じ解釈。Grok の `ui.timestamps` の実効値、OpenCode のオブジェクト形式の `model` の文字列表記）が `base` と違い、保存する値とも違う項目があれば、`conflict` と `conflictKeys` を返して何も書かない（`staleSettingsKeys`）。他の項目だけの変更は差分として反映する。読み取りから書き込みまでの間に変わった場合は `conflictKeys` なしの `conflict` を返す。画面は `SettingsConflictDialog` で再読み込みか編集に戻るかを選ばせる。再読み込みは `conflictKeys` の項目をファイルの値にし、他の項目の未保存の編集を残す。

**WSL（`common/wsl/wslFileScripts.ts`、`wslTransferScripts.ts`、`WslDetector.ts`）:**

- 厳密な読み取り、原子的な書き込み、削除、移動、改名、一覧、リンクの判定、ZIP の内容の読み取りと取り込みは、UNC に届くかにかかわらず distro 内のスクリプトで行う（UNC 越しではリンクの判定と rename の原子性に頼れないため）。`exists`、`readText`、`dirStats`、`listDirs` などは UNC を優先し、届かなければ wsl コマンドで実行する。UNC に届かなくても使えないのは、OS のプロセスへパスを渡すファイルマネージャーでの表示（`resolveRealPath`）だけ。
- 必須コマンド: `WslDetector.getMissingCommands` は、エージェントを使っている distro のうち `wslRequiredCommands.ts` の必須コマンドが足りないものを返す。`find`、`stat`、`readlink` は GNU 版のオプションも確かめる。distro ごとに一度だけ調べ、再取得で調べ直す。`WslMissingCommandsNotice` が画面の上部に表示する。bash の無い distro は対象にしない。
- ロックの判定: `lock_state` は `flock`、無ければ `lsof`、どちらも無ければ保持中とする。`lsof` は標準出力と標準エラーがどちらも空のときだけ空きとする。
- 目印: `withOutputMarkers` はスクリプトを `set +e +u +C` のあと `__AGENT_CLI_DEVKIT_OUTPUT__` の行と `__AGENT_CLI_DEVKIT_OUTPUT_END__` で挟み、スクリプトの終了コードを保つ。ログインシェルの出力は目印の外になる。`runInDistro` は先頭の目印を必須とし、`runMarkedScriptInDistro` は前後の目印を必須とする（そろわなければ `EWSLOUTPUT`）。`resolveHome` は `/` で始まる単一行だけを受け付ける。
- スクリプトの実行: これらのスクリプトは引数ではなく標準入力で `bash -l -s` へ渡すので、長さの制限を受けない。本体は関数にまとめ、途中で入力が切れると構文エラーになって何も実行しない。標準入力を閉じて実行し、エラーコードは `LC_ALL=C` のメッセージから求める。wsl.exe の出力の上限は 256 MiB。
- 読み取り: 本文を base64 で出力し、`sha256sum < file` の結果と照合する。途中でファイルが置き換わると `EINTEGRITY` になるので 1 回だけ読み直す。
- 書き込み: 本文は 1 MiB までは base64 のヒアドキュメントで渡す。これより大きな本文は、bash がスクリプトを 1 バイトずつ読むので、スクリプトの全体を `{ }` にまとめて先に読ませ、後ろに続く標準入力を `head -c` で読む（`runMarkedScriptInDistro` の `input`）。読み残しがあっても `exit` で終わるので、本文がコマンドとして解釈されることはない。一時ファイルの sha256 を確かめてから、置き換えの直前に `expectedRevision` と比較する。ハードリンクは元の内容を `.bak` へ退避してからその場で書き込み、失敗したら元の内容へ戻す。
- 一日より古い一時ファイルの削除とハードリンクの巻き戻しは、native の `writeFileAtomic` と distro 内の `buildWriteScript` の両方が行う。

**TOML のスコープ編集（`main/utils/tomlSubtree.ts`）:**

- `tomlStatements.ts` の走査で求めた範囲だけを切り貼りし、スコープ外の文をバイト単位で保つ。値は原文のまま扱い、整数表記と小数表記を変えない。`parseToml` は 2^53 を超える整数を bigint で読む。
- スコープは見出しのブロック（配列テーブルと配下の見出しを含む）と、親の本文にある行単位の文（ドットキーなど）。キーの引用形式を問わず完全パスで比較する。
- `readTomlTable`: 見出しのブロックだけなら原文（コメントを含む）を切り出す。親の本文にある文を含むときは見出しを補って組み立て、`normalized` を立てる。保存するとコメントを失うので画面に注記する。
- `replaceTomlTable`: 断片はブロック形（最初の文が対象か配下の見出し）か値形（最初の文が対象自身への代入）。ブロック形は最初に消した見出しブロックの位置に入れ、無ければ末尾に追記する。断片が null ならスコープを消し、空テーブルを残さない。`excludePaths` の配下は変更しない。
- `readTomlValue`、`replaceTomlValue`、`setTomlValue`: テーブル以外の値を値の範囲だけ置き換え、キーの表記と行末コメントを残す。null は代入の行を消し、親のテーブルは残す。
- `verifyTomlEdit`: 書き込む前に、パース結果の厳密比較（`strictDeepEqual`。空テーブルも区別する）、スコープ外の文の順序と原文の一致、スコープ内の数値の表記の一致を確かめる。
- 拒否する形: `invalid-existing`（既存のファイルが読めない）、`invalid-input`（断片が読めない）、`outside-scope`（断片が対象の外を定義する）、`forbidden-subpath`（除外した位置を含む）、`fragment-needs-header`（断片の先頭が対象の見出しでない）、`inline-parent`（親がインラインテーブル）、`unsupported-form`（配列テーブルの内側、親の本文に除外した位置があるなど。`already-defined` もこのコードで返す）、`verify-failed`。画面は直接編集へ案内する。

**JSON のスコープ編集（`main/utils/jsoncEdit.ts`、`ProfileManager`）:**

- `readJsoncScope` は値の原文を返す。`setJsoncRaw` は値の生テキストを置き換えるので、スコープ内のコメントと未知の項目を保ち、改行をファイルに揃えて継続行にインデントを付ける。`removeJsoncProperty` の `cascade: false` は親を空のまま残す。
- `editJsonValue` は編集の結果を読み直し、変更を適用したモデルと `strictDeepEqual` で一致することを確かめる（`verifyJsonEdit`）。途中にオブジェクト以外の値があれば `unsupported-form` で拒否する。
- 形式が `json` の文書（hooks.json など）の断片は `JSON.parse` で検証する。文書にコメントなどがあり CLI が読めない可能性があれば `existing-not-strict-json` で確認する。この確認は `applyDocEdit` が行うので、スコープ編集、`commandFields`、`orderedLists` の内容が変わる保存すべてに効く。形式が `jsonc` の文書はコメントを受け付ける。
- 2^53 を超える数値は原文のまま保つ。

**BOM の規則:**

- 読み取りでは BOM を除いて解釈し、`hadBom` を保持する。編集テキストの BOM は除く（`normalizeEditedText`、`saveDirectEdit`）。
- 保存では、読み取ったファイルの BOM を見つけたときの形のまま書き戻す（`withBom`）。新しいファイルは BOM を付けない。
- 例外はプロファイル設定の保存で BOM を付けないファイルで、`hooks.json`、`lsp.json`、`sidecar.json`、`*.rules`、`hooks` フォルダーの `*.json` が当たる（`isBomFreeFile`）。ZIP で取り込むこれらのファイルも BOM を除く（`dropStagedBom`）。
- Grok の `.js` ワークフローに BOM があれば `grok-workflow-bom` で確認する。

### 3.10 クリーンアップのプロジェクト単位の行

「プロジェクト」はワークスペースのパスを指し、各 CLI のプロジェクト ID や利用者が付けた名前を基準にしない。パスを特定できないものは「パス不明」の行にし、推測したパスは出さない。読めないものは消さず、パス不明か既存の行に残す。

**共通の扱い:**

- 行の形: `CleanupChild` の `name` は候補内で一意の識別子（多くは比較キー）で、`displayName` が表示するパス。`pathUnknown`、`pathUnknownLabelKey`、`badges`（`trusted`、`untrusted`、`trustUnset`、`mcpServers`、`duplicateKeys`、`grants`、`sessions`、`savedApprovals`）、`sharedPaths`、`relatedChildren`、`children`、`threadCount`、`mtimeMs`、`sizeUnknown` を持てる。候補は `confirmWarningKey` と `noticeKey` で削除の確認と行の注記を指定する。
- 削除先: 画面から受け取るのは行の識別子だけで、削除先は常に走査で得た実エントリから作る。
- 一覧に無い名前: Claude、Codex、Grok の行で、選択された名前に一致する行やキーが無ければ、成功にせず `skipped` で返す。
- 承認: Claude の `deleteSelected` は最初に `prepareClaudeLayout` で承認を反映した構成を調べ、候補の処理の順に関わらず同じ構成を使う。
- 削除の結果の通知: `cleanupOutcome` が選択の各項目を削除の前後の一覧で比べて、消えた数と残った項目を数え、`cleanupOutcomeNotice` が文言を選ぶ。すべて消えて失敗も無ければ各画面の成功の文、消えたものが無ければ `common.cleanupNothingDeleted`、一部だけなら `common.cleanupPartlyDeleted` を残っている名前（3 件まで、超えた分は件数）と一緒に警告として出す。承認の確認で外した結果、消すものが無くなったときは削除を呼ばず、選択を残す。
- Codex の日付単位の確認文: `sessions` と `archived-sessions` の `confirmWarningKey` は、状態 DB の行を消せるときは `confirmWarning.sessions`、DB が使えない環境（`layout.dbDirs` が空）では `confirmWarning.sessionsNoDb` にする。
- 表の列: `CleanupTableParts.tsx` がファイル数とサイズの列の幅を決め、候補の行、子要素の行、環境、その他のツールの表で数字の位置を揃える。
- CLI の停止の前提: 次の表の行は、Claude の `projects` を除いて CLI が起動していない前提で、使用中の判定、承認の問い合わせ、ロックの取得を行わない。起動中に操作すると、記録が再作成されたり、同時に書かれた変更が失われたりすることがある。
- データベース: データベースのファイル自体は候補にしない。読み書きは `common/sqlite/sqliteStore.ts` の `SqliteStore` を通し、Codex、Agy、OpenCode のロジックは環境で分けない。実装は `createSqliteStore` が環境から選ぶ（下記）。一日より古い読み取りのコピーは、Codex と共通基盤（Agy / OpenCode）のスキャンの開始時に `removeStaleCopies` が消す。

**データベースの読み書き（`common/sqlite/`）:**

- インターフェース: `read`（読み取りの手段を渡す）、`readEach`（複数のデータベースで同じ文を実行する。読めないものは null）、`write`（計画の読み取りの後に文を 1 つのトランザクションで実行する）、`existingDatabaseFiles`、`availability`、`removeStaleCopies`。BLOB は SQL の `hex()` で受け取る。
- `NativeSqliteStore`: `node:sqlite` を使うときに初めて読み込む。読み取りは `-wal` があれば `withDbCopy` が .db と -wal を一時フォルダーの `agent-cli-devkit-db-copy-*` にコピーして開き（POSIX は所有者だけが使える権限にする）、無ければ読み取り専用かつ `immutable=1` で開く。書き込みは実ファイルを 1 つの接続で開く。
- `WslSqliteStore`: distro の `sqlite3` コマンドを、標準入力で渡す前後の目印付きのスクリプトで実行する。データベースの内容のコピーは distro の中にだけ作る。
    - 検出: `type -aP sqlite3` の最初の `/mnt/` 以外の場所、`--version`、JSON の出力の実行結果を distro ごとに一度だけ調べる（`WslDetector.factOfDistro`。更新で `invalidate` されるまで保持し、調べられなかった場合は保持しない）。3.33 より古いか JSON の出力を使えなければ `too-old`。
    - 起動: `-batch -bail -init /dev/null` で `~/.sqliterc` を読まない。SQL は base64 で渡し、シェルの解釈を受けない。
    - 値: `?` を SQL のリテラルに置き換える（`inlineParams`）。文字列はシングルクォートを重ね、制御文字を含むものは `CAST(X'..' AS TEXT)` にする（`sqlite3` は行の単位で読み、CR を落とすため）。IN の値は 500 件ごとの文に分ける。
    - 読み取り: `-wal` が無ければ `-readonly` と `immutable=1`（`-wal` と `-shm` を作らない）。`-wal` と `-shm` があれば `-readonly` と `mode=ro` で実ファイルを開き、ロックや読み取り専用のエラーならコピーを読む。`-shm` が無ければコピーを読む（開くと `-shm` を作るため）。コピーは `mktemp -d` の所有者だけが使えるフォルダーに置き、`trap` でシェルの終了時に消す。出力は `.mode json` で、文ごとに `.print` の区切りを入れ、最後の区切りが無ければ失敗にする。
    - 書き込み: `.bail on`、`PRAGMA foreign_keys=ON`、外部キーが有効なことの確認（一時テーブルの CHECK）、`BEGIN IMMEDIATE`、計画の読み取りの行数の確認、文、`COMMIT` の順に実行する。終了コードが 0 で COMMIT の後の区切りが出力された場合だけ成功にし、それ以外は失敗で、接続を閉じるので何も確定しない。読み取りと書き込みは別のプロセスになるので、計画の後に行数が変わっていれば何も確定しない。パスが通常のファイルでなければ `sqlite3` を起動しない（新しいデータベースを作らない）。
- `sqlite3` を使えない distro: データベースが無いと使えない行（`session-projects`、Agy の `projects`、OpenCode の `projects`）は `blocked` の候補にして行と注記（`common.cleanupSqlite.blocked.*`）を表示し、選択できない（`CleanupHandler.blocked`、`toBlockedCandidate`）。データベースが無ければ、行の読み書きが無いので `blocked` にせず、注記も出さない。ファイルを消せる行（Codex の `sessions` と `archived-sessions`、Agy の `conversations`）は行を残さず注記（`common.cleanupSqlite.filesOnly.*`）を表示する。`blocked` の候補の選択は main 側でも拒否し、消せなかったものとして返す。
- FTS5: `conversations_fts` を読むと「no such module」になる `sqlite3` では、そのテーブルを飛ばして他の行を消し、`failedPaths` に `conversation_summaries.db (conversations_fts)` を入れて伝える。致命的にしない。

**Claude のパスの解決（`claudeProjectPaths.ts`、`claudeTempCleanup.ts`）:**

- 全体設定ファイル: `resolveClaudeGlobalConfigRel` が CLI と同じ規則で選ぶ。`~/.claude/.config.json` が通常のファイルでサイズが 0 より大きいか、書き込み可能で `~/.claude.json` が無ければ `~/.claude/.config.json`、それ以外は `~/.claude.json`。
- セッションのパス: 会話記録の末尾 64 KiB の最後の `relocated` 行の `relocatedCwd`、無ければ先頭 64 KiB の最初の `cwd` を読む。絶対パスで、順方向に変換してプロジェクト名と一致するものだけを採用する。
- 順方向の変換: `projectNameCandidates` は表示の形から `encodeProjectName` を計算し、Windows はドライブ文字の大小の両方を候補にする。プロジェクト名の比較は Windows で大文字小文字を区別しない。名前からパスへの逆算はしない。
- 表示: `ProjectPathBook` が 1 回のスキャンの綴りを比較キーごとに集め、全体設定ファイルのキー、セッションの作業フォルダ、その他の順に優先して 1 つに決める。Windows は `\` 区切りでドライブ文字を大文字にする。
- プロジェクト名の衝突: 別のパスが同じプロジェクト名になることがあるので、会話記録はセッション単位で行に分ける。`cwd` を読めないセッションは常にプロジェクト名のパス不明の行へ入れ、パスの行がパス不明のセッションを消さないようにする。セッションに結び付かないエントリは、そのプロジェクト名に対応するパス（会話記録と全体設定ファイルのキーの和集合）が 1 つならそのパスの行へ、それ以外はプロジェクト名のパス不明の行へ入れる。一覧できないプロジェクト名も同じ行に入れて、使用中の可能性があるものとして扱う。MCP ログは分けられないので、同じ名前に複数の行があれば行に含めず、その名前の行をすべて消すときだけ消す。
- 削除先: 常に一覧で得た実エントリから作り、表示パスや `cwd` から作らない。

**Claude のメモリの分離:**

- プロジェクト名の直下の一覧で `memory` とそれ以外のエントリを分ける。`projects` の行の削除はエントリ単位で行い、`memory` を対象にしない。最後に、その名前のすべての行を消すときに限って `memory` へ空ディレクトリの削除をかけ、プロジェクト名のディレクトリへ空ディレクトリの削除をかける。中身があれば失敗して残るので、一覧の取得失敗や判定後の書き込みでもメモリを消さない。
- `memory` 以外のエントリも一時物も無いプロジェクト名（空のディレクトリを含む）は `projects` の行に出さない。`orphan` の判定とサイズの合計も `memory` を含めない。
- `project-memory` の行に出す条件は、`memory` の配下にディレクトリ以外のエントリがあり、相対パスのどの要素もドットで始まらないものが 1 件でもあること（`hasUndottedEntries`）。ドットファイルだけのメモリには行が無い。サイズと削除の対象はドットファイルを含む全体。プロジェクト名ごとに 1 行で、複数のパスが一致すれば改行で並べて一緒に消す。パスが無ければ、他のセッションのパス、登録の作業フォルダ、`githubRepoPaths`、入力履歴の `project` とそれぞれの祖先を順方向に変換して探し、見つからなければパス不明にする。削除後にプロジェクト名のディレクトリへ空ディレクトリの削除をかける。
- `autoMemoryDirectory` の指定先は扱わない。

**Claude のプロジェクト記録（`claudeProjectRecords.ts`）:** 比較キーが同じキーを 1 行にまとめ、信頼状態と MCP の件数をキーごとに集計する。値は renderer に送らない。削除は直前に読み直して厳密な JSON として解析し、失敗すれば何も書かない。該当キーだけを切り取るので、大きな数値の精度、形式、末尾改行の有無を保つ。結果を `strictDeepEqual` で確かめ、一時ファイルと rename で置き換えて権限を引き継ぐ。途中で内容が変わっていれば読み直してやり直す。

**Codex のセッションと削除（`codexThreadLayout.ts`、`codexSessionCleanup.ts`、`codexThreadDeletion.ts`、`codexStateDb.ts`）:**

- 表示の切り替え: `SessionViewToggle` で日付とプロジェクトを切り替える。`session-projects` の候補が無い場合（`node:sqlite` を読み込めない環境、`threads` に `id` か `cwd` が無い DB がある環境、行が 0 件の環境）は日付の表示だけになる。`sqlite3` を使えない distro では切り替えを残し、プロジェクトの表示に `blocked` の行と注記を出す。データベースを扱えない環境では `sessions` と `archived_sessions` の行に注記（distro は `common.cleanupSqlite.filesOnly.*`、native は `codex.cleanup.notice.stateDbUnavailable`）を添え、データベースの段階を飛ばす。

- 削除の順序（`deleteCodexThreads`）: 次の順に消し、ある段階が失敗したら、それより後の段階へ進まない（残った行とファイルからやり直せるようにするため）。
    1. `thread_history_1` の行（スレッド ID とロールアウト ID）
    2. `sessions` と `archived_sessions` のセッションファイル（消せなかったスレッドは以降の対象から外す）
    3. `session_index.jsonl` の該当行
    4. `logs_2`、`queue_1`、`memories_1`、`memories_v2_1`、`goals_1` の行、最後に `state_5` の行（`threads` の行を最後に消す）
    5. `history.jsonl` の該当行、`shell_snapshots/<ID>.*`、`visualizations/YYYY/MM/DD/<ID>/`、`thread-writer-locks/<ID>.lock`

- プロジェクト記録（`codexProjectRecords.ts`）: テーブルごと切り取り、空のテーブルを残さない（`removeTomlTables`）。テーブルの直上のコメントはそのテーブルの説明として一緒に消える。同じ比較キーのテーブルをまとめて消し、他の文をバイト単位で保つ。

**Agy のプロジェクトの行（`agyProjectCleanup.ts`、`agyTrajectoryMetadata.ts`、`agyConversationDb.ts`、`agyWorkspacePath.ts`、`agyConversationArtifacts.ts`）:**

- 行の単位: 会話のパス、変更してよい定義の `folderUri`、`history.jsonl` の `workspace`、`cache/last_conversations.json` のキーの和集合で、正規化したパス 1 つにつき 1 行。親や子のフォルダーにはまとめない。

- 消す範囲（会話 ID ごと）: `conversations/<id>.db`、`-wal`、`-shm`、`brain/<id>`、`annotations/<id>.pbtxt`、`chapter_titles/<id>.pb`、`voice_chats/<id>.json`、`browser_recordings/<id>`、`worktrees/<id>`。worktree は `git worktree remove --force` で登録から外してから消す（git が無ければ飛ばす。WSL は distro の git）。`conversation_summaries.db` の `conversation_summaries` と `conversations_fts` の行もベストエフォートで消す（`removeAgySummaryRows`。`sqlite3` を使えない distro では残す）。同じ ID の `.pb` が残る会話の付随データには触らない。
- 消す範囲（パスごと）: `history.jsonl` の該当行と `conversationId` が一致する行（他の行はバイト単位で残す）、`cache/last_conversations.json` の該当キー、`~/.gemini/config/projects/<id>.json` の該当する `folderUri` の要素。残る要素が無ければ定義のファイルを消す。
- 変更しない定義: `default-cli-project`、`outside-of-project`、`cache/default_project_id.txt` の値、`~/.gemini/config/config.json` の `sidecars.*.projectId` に該当する定義。行の材料にもしない。これらの ID を判定できなければ定義をどれも変更しない。これらに属する会話はパスで消す。
- 要約 DB: `removeAgySummaryRows` は `conversation_summaries` と `conversations_fts` の行を 1 つのトランザクションで消し、失敗したら元に戻して `failedPaths` に DB のパスを入れる。ロックの解放を 2 秒待つ。
- 要約キャッシュ: `removeJetboxEntries`（`agyJetboxSummaries.ts`）は `jetbox_summaries_proto.pb` から消す会話の項目を取り除く。形式はフィールド 1 の項目の並びで、項目はキーのフィールド 1（会話 ID）と値のフィールド 2 を持つ。読み書きは `@bufbuild/protobuf/wire` の `BinaryReader` と `BinaryWriter` で行い、スキーマを使わない。残す項目の中身はそのまま書き戻す。全体がこの形で読めなければ変更せず、`failedPaths` にパスを入れる。最後の項目を消すと 0 バイトのファイルが残る。
- 触らないもの: `implicit`、`knowledge`、`scratch`、App の会話。
- 確認文: 通常の削除確認だけで、特別な警告を入れない。

**Agy のその他の行:** `trusted-workspaces` は要素の文字列そのものを行の名前にし、完全に一致する要素だけを消す。すべて消した配列は `[]` として残す。`cache` はフォルダごと消す。`conversations` の行の削除は `afterDelete` で、本体（`.db` と `.pb`）が残っていない会話の残りのファイル、付随データ、要約 DB の行を消す。`sqlite3` を使えない distro では要約 DB の行が残り、行の注記で伝える。

- `sessions/<enc>` の復号: `decodeURIComponent` の結果が環境の絶対パスの形ならそれを使う。違えば `.cwd`、次に各セッションの `summary.json` の `info.cwd`。どれも使えなければディレクトリ名のままパス不明にする。同じパスのディレクトリは 1 行にまとめ、許可のファイルの件数を `grants` で示す。

- 行の単位: `project.worktree`（`global` を除く）、`worktree.directory`、`project_directory.directory`、セッションのルートの和集合で、比較キーごとに 1 行。1 行が複数の `project_id` を持つことがある。セッションのルートは `session_v2.directory` の末尾から `path` を除いて求める。`path` が NULL のセッションは同じプロジェクトの既知のパスで最も長く一致するものに入れる。`directory` が空のセッションは行に入れず、`sessions` の行に残す。

- 行の表示: `sessions` の件数と、最後のパスのときの `savedApprovals` の件数。大きさは取得しない。

### 3.11 実行で確認できていない挙動

CLI の実行による確認は途中で打ち切り、以後どの CLI も起動していない。実行で確定したのは次の点だけである。

- Grok 1.0.70 のフック名の形（`global/<stem>:session_start[0].hooks[1]`、`user:session_start[1].hooks[0]`）。
- Codex の `[hooks]`: 型違い（スカラー、`matcher` の整数、`hooks` のスカラー、`timeout` の文字列、負数、小数）、`type` の不正値や欠落、`command` の欠落は起動エラーになる。未知のイベント、未知のキー、不正な matcher の正規表現は起動できる。`hooks.state` の型違いも起動エラーになる。
- Codex の `config.toml` は BOM と CRLF があっても読める。

次は CLI を実行して確かめていない。読めないものは消さずパス不明か既存の行に残し、形式を断定しない表示にし、保存前の検証は確定した範囲だけ拒否してそれ以外は警告にとどめる。

| OpenCode | 実データのセッション行の形、`project` の行のカスケードの範囲（保存済みの承認を含む）、削除後の CLI の再起動と行の再作成、CLI が作った WAL の DB を Electron で編集できること、スナップショットの sha1 の入力、空のコマンドと空の `AGENTS.md` の登録 |

## 4. 設定編集レジストリ

設定項目の追加・廃止の判定基準（公式一次情報の参照先、マネージド専用・非推奨の除外、型の割り当て、実装手順）は `設定項目メンテナンス方針.md` に定める。本節はレジストリの構造・型・保存の仕組みのみを記す。

- Claude: `shared/agents/claude/constants.ts` の `SETTINGS_FIELDS`（`~/.claude/settings.json` の表示・編集対象項目）。envFlag 型（env 内キーの ON/OFF）に対応。
- Codex: `shared/agents/codex/constants.ts` の `SETTINGS_FIELDS`（`~/.codex/config.toml` のドット区切りキー）。
- Agy: `shared/agents/agy/constants.ts` の `SETTINGS_FIELDS`（`~/.gemini/antigravity-cli/settings.json` のトップレベルキー）。Antigravity IDE や互換ディレクトリの設定を含めない。
- Grok: `shared/agents/grok/constants.ts` の `SETTINGS_FIELDS`（`~/.grok/config.toml` のドット区切りキー）。
- OpenCode: `shared/agents/opencode/constants.ts` の `SETTINGS_FIELDS`（OpenCode 2 のグローバル設定ファイル `opencode.json` / `opencode.jsonc` のキー。編集対象ファイルの決め方は §3.5）。`model` は文字列とオブジェクトの union だが、表では文字列として編集可能にしている（§3.5）。互換ディレクトリ、TUI 専用の `cli.json`、バックグラウンドサービスの `service.json` の設定を含めない。
- いずれも registry へ 1 項目追加すると UI 表示へ反映される。設定画面のグループ見出しは `group` ごとにまとめ、`SETTINGS_FIELDS` でそのグループが最初に現れた順に表示する。型は boolean / string / number / Claude の envFlag / enum（型が混在する固定候補から 1 つを選ぶ。候補ごとに値と型を持ち、選んだ値を型のまま読み書きする。例: Grok の `features.telemetry` の `true` / `"session_metrics"` / `false` / `"off"`）に加え、配列・オブジェクト・動的テーブルなど一覧表示専用の directEdit を扱う。編集可能型は読み取り・テーブル編集・保存まで反映される。タブや別の画面で編集する項目は、型を directEdit のまま `linkTab` か `linkRoute` を付けたリンク行にする（§3.8）。
- 値の制約: number 項目は `integer`（整数だけ）・`min` / `max`（範囲）・`exclusiveMin`（`min` を範囲に含めない。例: Claude の `skillListingBudgetFraction` は 0 より大きく 1 以下）、string 項目は `pattern`（形式。例: OpenCode の `model`）を宣言できる。検証は `shared/agents/settingsValue.ts` の `settingsValueProblem` で行い、制約に合わない値は丸めず保存しない。画面の数値欄は入力中の文字列をそのまま表示し、フォーカスを外したときに形式・範囲に合わない値をエラー表示にする。保存時は最初の不正な値の項目名と受け付ける範囲（または整数・数値であること）を通知して保存を中止し、main 側も同じ検証で `invalid-value` を返して書き込まない。
- 選択候補は二種類ある。厳密な列挙値はセレクト、モデル ID・テーマ・プロバイダ ID など拡張可能な値は候補付き自由入力として表示する。厳密な列挙値でも、将来の CLI や外部編集で保存された候補外値を空欄にせず「保存済み値」として表示する。
- 選択候補の先頭は未設定を表す。公式資料または公式ソースで固定既定値を確認できた項目は「未設定（既定: 有効/無効/<値>）」と表示し、環境依存・モデル依存・未記載の項目は「未設定」のまま表示する。文字列・数値・候補付き自由入力には未設定や入力例の placeholder を表示しない。
- 表示対象は Claude 163 項目（編集可能 115 / directEdit 48、うちリンク行 14）、Codex 166 項目（編集可能 121 / directEdit 45、うちリンク行 7）、Agy 32 項目（編集可能 25 / directEdit 7、うちリンク行 5）、Grok 262 項目（編集可能 219 / directEdit 43、うちリンク行 6）、OpenCode 41 項目（編集可能 24 / directEdit 17、うちリンク行 6）。各項目は日本語・英語の双方に短い名称と項目固有の説明を持つ。
- Grok の `ui.timestamps` を保存するとき、ファイルにレガシーキー `ui.show_timestamps`（Grok が書き込みのたびに同期する on/off の写し）があれば同じ内容（`off` 以外は `true`）にそろえ、`ui.timestamps` を未設定に戻した場合はレガシーキーも削除する（`[ui]` で両者が矛盾すると `ui.show_timestamps` が優先されるため。`GrokConfigManager`）。
- 同一設定に正規キーと別名が両方ある場合は正規キーのみを登録する。Claude の `permissions.disableAutoMode`（トップレベル `disableAutoMode` の別名）、Codex の `agents.max_threads`（`agents.max_concurrent_threads_per_session` の別名）は登録しない。
- キー名自体にドットを含む設定は、ドット区切り path でネストキーと区別できないため登録しない（例: Codex の `notice.hide_gpt-5.1-codex-max_migration_prompt`）。直接編集で扱う。
- 項目の説明文は「その設定を変えると何が起きるか」だけを書く。編集可能なスコープ（プロジェクト設定では無視される、管理設定でのみ有効など）は、本アプリがユーザープロファイルの設定ファイルだけを対象とするため記載しない。値の型を述べただけの説明や「配列なので直接編集します」といった操作方法の案内も書かない（値欄に編集先へのリンクか「ファイルを直接編集」を表示するため）。
- テーブル保存は、読み込み時の値と比較してユーザーが変更した編集可能値だけを main プロセスへ送る。main 側も入力に存在する編集可能項目だけを書き戻し、directEdit は renderer / main の双方で保存対象外にする。この二重の差分適用により、未対応の新規設定、TOML の inline table、JSON/TOML のオブジェクト・配列を別項目の保存で削除しない。
- 文字列・数値入力を空欄にすると renderer は変更値を `undefined` として送る。Claude / Agy / OpenCode は対象 JSON キー（Claude の envFlag は対象 env キー）を削除し、Codex / Grok は対象 TOML scalar を削除するため、空文字列としては保存せず未設定へ戻す。編集前から未設定の空欄は差分に含めない。
- JSON/TOML のオブジェクト、配列、動的テーブル、Codex の granular approval policy など構造値は設定一覧にも項目として表示し、値欄へ編集先へのリンクか「ファイルを直接編集」を表示する。画面上部には編集方式を説明する全体メッセージを表示しない。直接編集はファイル全体を構文検証し、開いた後に変わっていなければ保存する。通常保存でも既存 JSON/TOML が壊れている場合は書き込みを拒否し、表の代わりに読めない理由を表示する（`SettingsFileBanner`）。Claude の `settings.json` と全体設定ファイルは厳密な JSON として読み、CLI が読めないコメントや末尾カンマがあれば `invalid-existing-json` を返す。
- Claude の `model` / `advisorModel` は公式 alias、正式 Anthropic model ID、Bedrock ARN、Foundry deployment、Agent Platform version、ゲートウェイ固有 ID を受け付ける。Codex と Grok のモデルも動的カタログまたはカスタムプロバイダを考慮し、候補外 ID を許可する。

## 5. データモデル

本アプリは自身のデータベースを持たない。操作対象は各 CLI ツールの設定ファイル（JSON / TOML / YAML）とディレクトリで、クリーンアップの一部の行は CLI の SQLite データベースの行を読み書きする（native は `node:sqlite`、WSL は distro の `sqlite3` コマンド。§3.10）。アプリが管理する永続データは次のみとする。

- MCP の無効化ファイル（sidecar）: Claude Desktop `claude_desktop_config_disabled.json` / Claude Code `~/.claude-disabled-mcp.json` / Codex `~/.codex/config-disabled-mcp.toml` / Agy `~/.gemini/config/mcp_config_disabled.json` / Grok `~/.grok/config-disabled-mcp.toml` / OpenCode `~/.config/opencode/opencode-disabled-mcp.json`（`origins` に元のファイル名と隠れていた定義を持つ）。
- OpenCode Plugin の無効状態（公式仕様に保存項目がないため）: `~/.config/opencode/opencode-disabled-plugins.json`（`{ plugins: [...], positions: { <指定子>: { origins: [{ file, items, order }] } } }`。元のファイルが分からない記録は無効化した時点の並びの配列）と `~/.config/opencode/plugins-disabled/`。
- アプリ設定（`~/.agent_cli_devkit/settings.json`）: テーマ `theme` / 言語 `language`。
- ダッシュボードの展開グループ: renderer の localStorage（`dashboard.expandedAgent`）。

## 6. agent 追加ガイド

新しい agent CLI（例: `gemini`）を追加する場合、以下の「agent 別ディレクトリの追加 + 登録ポイントへの 1 行追加」で完結する。

1. **shared** — `src/shared/agents/gemini/{constants,types,ipc}.ts` を作成。
    - 登録: `src/shared/ipc.ts` の `IpcApi` に `gemini: GeminiIpcApi;` を追加。
2. **main services** — `src/main/services/gemini/` にマネージャを実装。共通処理は `services/common/`（`WslDetector.getDistrosWithTest()` / `HomeFs`）と `main/utils/` を利用。
3. **main ipc** — `src/main/ipc/gemini/` にハンドラと `index.ts`（`registerGeminiIpcHandlers`）を作成。
    - 登録: `src/main/ipc/index.ts` に 1 行追加。
4. **preload** — `src/preload/agents/gemini.ts` にブリッジを作成。
    - 登録: `src/preload/index.ts` の api に `gemini: geminiApi,` を追加。
5. **renderer** — `src/renderer/agents/gemini/` に画面コンポーネントと `index.tsx`（`AgentModule` 定義: ルート/アイコン/文言キー。グループ名も `labelKey` の文言キーで指定する）を作成。
    - 登録: `src/renderer/agents/index.ts` の `AGENT_MODULES` に 1 行追加。ダッシュボード・タイトルバー・ルートは自動反映される。
6. **i18n** — `src/renderer/i18n/locales/{ja,en}/gemini.ts` を作成し、各 `index.ts` に 1 行追加。文言キーは `gemini.*` 名前空間。
7. **プロファイル設定タブ** — `src/shared/agents/gemini/profileTabs.ts` に `AgentProfileSpec` を定義し、`src/main/ipc/gemini/index.ts` で `registerProfileHandlers(profileChannels('gemini'), new ProfileManager(detector, spec), getMainWindow)` を呼び、preload で `createProfileApi` を公開する。文言は `gemini.profile.*`（§3.8）。

## 7. ビルド・配布

- 開発: `yarn dev`（tsc watch + vite + electron。renderer は BrowserRouter / <http://localhost:3001>）
- 検証: `yarn lint`（tsc --noEmit）/ `yarn eslint`
- 配布: `yarn dist:win|mac|linux`（renderer は HashRouter / `dist/renderer/index.html`）
- リリース: `yarn release:win|mac|linux`（GitHub ドラフトリリースへアップロード）

## 8. セキュリティ上の注意

- BrowserWindow は `contextIsolation: true` / `nodeIntegration: false` を維持しつつ、preload の agent 別ファイル分割のために `sandbox: false` としている。renderer に公開する API は `window.agentCliDevkit` 経由の明示的なブリッジのみ。
- クリーンアップ・削除操作はすべて既定 OFF のチェックボックス + 確認ダイアログを経る。使用中ファイルは best-effort でスキップし、結果として報告する。
- プロファイル設定の main 側は `sectionId` を仕様と照合し、renderer から受け取るパスは検証した相対パスだけにする。`sensitive` の section は操作があるまで本文を返さず、MCP の一覧は環境変数とヘッダーの値を返さない。結果には本文を含み得る例外のメッセージを含めない。
